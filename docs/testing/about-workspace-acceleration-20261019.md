## 下载检查结论与接入

`config/update-kit.lock.json`（共享组件锁）固定 DesktopUpdateKit（桌面下载组件）提交 `8bfb24c1770098f6bd68aef208fcdfa1f097b92b`。该提交的原生 `DownloadOptions`（下载参数）默认 `max_connections=4`（最大四连接）、`parallel_threshold=16 MiB`（并行阈值）。本项目此前只复用它的 WinHTTP（系统网络库）传输，应用更新安装器和 GitHub（代码托管平台）组件归档没有接入上游四路调度。

本次保持锁定提交与上游检出不变，将本项目桥接与上游实现在同一编译单元构建，直接复用已有探测、四路分片、合并及单路下载函数。上游公开更新客户端要求额外下载独立摘要文件，不适用于本项目的通用资源清单，因此没有伪造该附件或改写资源身份。

应用更新安装器与 GitHub 组件资源通过原有公共下载入口接入：

1. 以原始 GitHub 地址判断资格，来源改写成镜像后继续生效。
2. 文件达到 16 MiB（16 兆二进制字节），且没有有效连续断点时，探测后使用上游四路算法。
3. 不支持范围时单路下载；四路响应失败时在同一来源回退单路，再由现有宿主控制来源恢复轮次。
4. 下载始终写入受管暂存文件，最终使用可信清单的 SHA-256 / SHA-512（文件摘要）完整校验后原子启用，失败保留旧缓存。
5. 有效连续断点继续原顺序续传，完整缓存复用；小文件与非 GitHub 来源沿用原下载方式。
6. 加速文件一次预留四个全局通道，其他传输等待。上游工作线程的进度通过调用线程转发，取消时中止网络并回收全部线程。

更新清单仍直连官方来源；构建准备中的 Git（源码管理工具）克隆、Python（后端语言）维护下载和脚本包管理器不属于这条原生加速入口。桥接引用锁定上游的内部函数，更新锁定提交后必须重新编译并验证此接入。
