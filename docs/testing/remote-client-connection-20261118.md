## 原因与修订

- 本机实际配置为 remote（远程模式）且 paired_host（配对服务端）为空。旧投影使用“已配对服务端”默认名称，断线时还把核心能力写为失败；新投影明确未配对、等待连接及暂停重连。组件页未取得服务端状态时显示等待，不发无效资源查询或本地组件修复操作。
- 旧投影将 can_start（允许开始监听）为假当作核心不可用，正常监听、思考及播报也会误报。现在按管理状态和服务端门禁能力状态判断，加载态使用大写 STARTING（启动中），启用中的可选能力不扩大为语音门禁失败。

- 每次独立管理请求原来创建新租约，前端却要求租约代次相同，造成有效响应被拒绝；高频查询也会耗尽会话容量。同一 SSH 连接现在复用管理申请，提前十秒轮换租约。新服务端声明 persistent_management（持续管理请求逐次核验信任）后才保持管理通道；旧服务端仍逐次开通道并核对身份，协议版本不变。
- 只读管理状态、资源盘点、任务补查及系统状态原来占用 512 项、保留 24 小时的写入幂等账本。现在只读请求读取当前状态，不占该账本；有副作用操作继续保留参数冲突拒绝、原编号结果重放及容量准入。租约申请记录随自身到期回收。
- 连续管理通道每次操作重新核验构建与设备信任，并强制请求代次属于本连接；撤销或角色/工作区交接后的旧请求不能继续进入新状态。客户端显式连接/断开使旧管理读取失效，原生回执也重新核对当前工作区和配置。
- 设备页与全局监督器原来各自维护重连计时器。现在只保留全局有界退避监督器；主动断开先持久暂停，接管导致暂停时重新读取当前配置，保留并发偏好且不覆盖新目标。原生配对、认证与模式/工作区维护使用同一任务准入边界，离页仍由宿主记录进度。
- 远程组件动作仅在原生管理连接可用后开放；连接恢复自动补查，目标交接清除旧清单、确认草稿与任务记录，丢弃迟到查询。组件页不消费客户端本机组件进度，保留客户端文件上传的原生进度。
