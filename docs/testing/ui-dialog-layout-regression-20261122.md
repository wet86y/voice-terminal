# 公共弹窗嵌套布局回归核验（2026-11-22）

## 问题与原因

用户反馈更新日志的版本卡片变成横条，标题与摘要被裁切。使用正式 `AppUpdateCard`（应用更新卡片）及随包 14 个版本的完整记录，在真实浏览器中复现。

上轮公共弹窗新增 `.dialog-body`（内容容器），并把任意插槽内容放入 Grid（网格布局）。历史列表原有自己的限高、网格、滚动与条目裁切，两层布局叠加后，14 条版本记录被分配到约 29 像素的行高。测得条目内部内容约 80 像素，可视内容高度只有 27 像素。版本数据和展开状态仍完整，故障来自布局，不是日志读取或更新检查接口。

将外层恢复自然文档流，或单独指定列表内容行高后，卡片恢复约 82 像素。负向验证重新注入上轮样式，新增回归立即报告 14 条记录全部被裁切，证明断言能够识别原问题。

上轮检查使用了通用长段落、资源弹窗与控件状态，没有渲染应用更新卡片的完整版本列表；DOM（文档对象模型）测试也不计算真实排版，因此未能发现这次回归。

## 验证与入口

`scripts/check-frontend-layout.mjs`（真实弹窗布局回归）组合正式组件与 `tests/fixtures/ui-dialog-layout.mjs`（固定数据夹具），仅监听本机测试页面，不连接正式程序；网络请求及业务写入在夹具中禁止。版本数从仓库实际发行文档发现，不截短列表来适配窗口。

`npm test`（常规回归）已接入该检查，也可单独运行 `npm run frontend:check-layout`（布局专项）。检查使用现有 Edge（浏览器），可通过 `VOICE_TERMINAL_LAYOUT_BROWSER`（渲染引擎路径）指定兼容引擎，不自动安装环境。

本轮前端 628 项、开发与调试入口 16 项通过；真实布局 22 项通过。版本历史覆盖 1200×900、960×720、390×600、800×360 四种窗口，其他实际组件覆盖大窗口、窄窗口与低高度窗口。断言包含条目未被压缩裁切、普通列表不重复限高、展开内容存在、末项可达、无水平溢出及底部操作完整可见。前端类型检查与正式构建通过。

截图、原样式失败证据、几何测量及本轮交付核验保存在 `.local/cache/reports/ui-dialog-regression`（专项报告目录）与 `.local/cache/reports/frontend-dialog-layout`（常规布局报告目录），不进入源码历史。
