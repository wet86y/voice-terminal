# CPU/GPU 设备热切换生命周期

本文记录详情页设备选择、后端接口、模型进程与运行操作状态之间的真实生命周期。运行提示沿用[在线切换与自动停听](runtime-switching.md)的公共状态契约；原有设备偏好结构不迁移。

## 范围和模型边界

| 模型 | 可热切换 | 加载进程与关联资源 |
| --- | --- | --- |
| Paraformer（流式语音识别） | 是 | ASR（自动语音识别）工作进程继续管理音频连接、转写和分段；流式推理模型运行在按需模型子进程。缓存以 `turn_id`（发言轮次编号）隔离，发言轮次结束或切换卸载时清理。双路离线精修已启用时和主路一起切换，保持相同实际设备；未启用时不得启动精修进程。 |
| emotion2vec（情绪模型） | 是 | 分析工作进程持有 emotion2vec 模型子进程；目标设备通过对应的 CPU（中央处理器）或 GPU（图形处理器）运行环境启动。 |
| CAM++（声纹模型） | 是 | 声纹工作进程按目标设备环境重启；进程缺失、由外部管理或目标资源不可用时，拒绝切换。 |
| FSMN-VAD、KWS、SmartTurn | 否 | 使用既有偏好保存与重启生效契约，不纳入本接口的热切换白名单。 |

应用服务与其他模型工作进程保持运行。热切换可重建被选中的模型进程，以释放其模型权重、原生库和设备上下文；Paraformer 双路模式会连同离线精修进程重建。

## 页面到接口

详情行“保存”只发送当前模型的 `model_id`（目标模型编号）与 `device`（目标运行设备模式），不提交其他行尚未保存的草稿。接口为：

```http
PUT /api/v1/product/settings/compute
Content-Type: application/json

{"model_id":"paraformer","device":"cuda"}
```

| 字段 | 中文说明 | 允许值 |
| --- | --- | --- |
| `model_id` | 本次切换目标模型编号 | `paraformer`（流式识别）、`emotion`（情绪模型）、`campplus`（声纹模型） |
| `device` | 目标设备偏好 | `auto`（自动选择）、`cpu`（中央处理器）、`cuda`（图形处理器） |

接口接纳切换后立即返回，不等待原生模型加载或推理预热。响应包括 `effective_from`（生效时机，值为 `immediate`）、`restart_required`（需要重启，值为 `false`）、`accepted`（已接纳，值为 `true`）、`operation_id`（对应运行操作编号）及 `pending`（该后台操作是否仍在处理中，初始为 `true`）。此处的 `pending=true` 表示后台切换仍在进行，不表示设置被留到下次应用重启；最终成功或失败以运行状态卡中的终态为准。

后端 `switch_compute_device`（单模型切换事务）为本次请求同步预约一个运行操作，再异步执行长耗时工作。界面保存按钮不等待推理框架初始化、原生库回收或模型预热；加载阶段会持续由同一运行操作发布进度。

## 后端事务顺序

1. **接纳与排队**：登记 `compute_device:<model_id>`（计算设备切换目标），发出操作快照；同一类计算设备切换由锁串行化。
2. **检查**：核对白名单、模型资源摘要、模型已由本应用加载、服务健康及预热状态。请求 `cuda` 时额外执行当前环境与逐模型 GPU 能力检查。检测到外部进程管理、缺失或未预热模型时直接失败，不写入新偏好。
3. **暂停输入**：使用公共 `runtime_operation`（运行操作作用域）登记组件名称和切换阶段，暂停新输入并等待正在进行的模型调用到达安全边界。保留操作开始时的监听意图。
4. **释放旧资源**：先让旧模型调用结束并清理轮次状态，再关闭目标模型子进程。Paraformer 开启双路精修时先关闭精修，再卸载主识别；主路迁移成功后以相同目标设备重新加载精修。模型子进程退出会一并释放该进程持有的权重和设备上下文。
5. **加载与预热**：根据 `auto`、`cpu` 或 `cuda` 选取设备环境并启动目标进程；执行模型自身的真实推理预热。`auto` 沿用启动时设备规则。显式请求 `cuda` 而模型报告实际 `cpu` 视为失败，不将静默回退报告为成功。
6. **核验与提交**：核对服务就绪、模型已加载、真实预热完成、实际设备符合请求；Paraformer 还核验已启用离线精修的状态与设备。只有核验通过后，才保存该模型偏好和最近成功设备，并更新内存中的运行配置。
7. **失败回滚**：加载、预热、核验或配置保存失败时，保持旧设置，按旧的保存偏好重建旧模型并核对其实际设备。回滚成功后报告原失败并恢复操作开始时的监听状态；回滚失败时撤销自动恢复，保持停听并报告两个错误。
8. **恢复监听**：事务成功或已成功回滚后，操作队列按原监听意图恢复输入；若操作前未监听，则继续未监听。运行卡片只在恢复过程结束后进入成功终态。

请求取消或应用关闭会遵循模型进程收尾与输入所有权规则；应用关闭时不重建旧模型。资源状态按模型子进程的真实 PID（进程标识）、工作集、提交量、显存和加载增量报告，主 ASR（自动语音识别）工作进程继续独立计量。

## 状态核验和持久设置

`GET /api/v1/product/compute-status`（读取硬件和实际模型状态）的模型记录包含：

| 字段 | 中文说明 |
| --- | --- |
| `service` | 模型服务状态；成功要求 `READY`（就绪） |
| `model_loaded` | 模型是否仍由存活进程加载 |
| `model_warmed` | 是否已通过模型真实推理预热 |
| `requested_device` | 进程收到的目标设备选择 |
| `device` | 模型实际运行设备 |
| `pid` | 当前模型进程标识；切换成功后应对应新进程 |
| `load_error` | 加载或设备回退的错误说明 |
| `resource_footprint` | 本次加载与预热的资源增量 |

成功状态不能只由页面保存完成、接口接纳或短暂显存占用推断；应检查服务就绪、模型已加载、`model_warmed=true`（真实预热完成）和目标实际设备。Paraformer 开启双路精修时，还需确认离线精修 `READY`（就绪）、已加载、已预热且 `device`（实际运行设备）与主路一致。运行操作终态、阶段和错误字段遵循[统一状态契约](runtime-switching.md#通用状态契约)。

持久化沿用 `compute.devices`（各模型运行模式）和 `compute.fallback_devices`（最近成功设备回退值）。接口一次只保存目标模型的两个相关值，不改变其他模型设置，也不做设置迁移。

## 与既有组件热切换路径的关系

本路径复用提交 `430bad9`（统一在线切换状态与监听恢复）接入的 `runtime_operation`（运行操作作用域）、同步操作预约、运行快照、监听暂停／恢复、阶段提示和失败终态。切换接口把耗时模型工作交给后台操作，并把 `operation_id`（运行操作编号）返回给页面，因此用户点击后由状态卡承接长时间加载过程；这也避免 HTTP（网页接口）请求和保存按钮一直停留在“保存中”。

设备切换比普通热切换多出严格的模型进程所有权、实际设备、真实推理预热与设备特定回滚检查。不能把“启动进程”“检测到显存”或“接口返回成功接纳”单独作为模型可用的结论。对于长时间加载，进度卡反映后台阶段；模型总体状态还应在核验完成后才从启动中转为就绪。
