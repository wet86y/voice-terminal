# DSH（代理执行宿主）包安装、兼容与迁移

DSH（代理执行宿主）通过 npm（包管理器）在线安装精确版本。当前目标为 `0.2.0-rc.2`，本轮已核验官方包归档及构建后的命令入口。正式程序及安装器携带目标配置、安装适配器和已编译项目插件；不内置官方桌面安装器或宿主根包，不建设在线程序推送系统。

## 配置与发布

唯一目标配置为 `config/dsh/runtime.lock.json`（宿主版本配置）。资源清单使用 `version_from`（目标版本配置来源），原生端和后端运行时读取目标版本；默认配置从同一配置读取兼容要求。`distribution`（分发声明）指定包名、注册表、适配类型、入口、必要资源、Node.js（脚本运行环境）范围与桥接协议，`package_manager`（插件包管理工具）指定工作区私有 pnpm（插件包管理器）版本。

源码标签与提交供维护者检出和构建，不作为 npm（包安装）宿主的启动条件。官方桌面来源和旧物理来源有独立的历史兼容记录、摘要和识别接口，修改新目标版本不会抹去旧来源的识别依据。

项目插件成功构建后生成 `dsh-compatibility.json`（宿主适配记录），记录 `dsh_version`（已适配宿主版本）、`adapter`（运行适配器）和 `bridge_protocol`（桥接协议）。构建检查源码和插件宿主依赖版本，程序包组装、安装候选检查及启动都核对适配记录。只提高目标版本而未重新适配、构建插件的组合不能发布。

后续发布顺序为：修改目标配置 → 检出对应官方源码 → 适配并构建项目插件 → 验证组合 → 构建统一程序包与分发安装器。更新入口或配置结构时扩展适配器，通用组件下载流程不修改特定版本值。

## 安装与运行

组件编号仍为 `dsh`（代理宿主组件），安装目录仍为 `runtimes/dsh`（工作区宿主目录）。缺失执行安装、目标组合不匹配执行更新、同版本损坏执行修复。安装在工作区独立候选目录进行，npm（包管理器）只安装配置中的精确宿主版本及工具版本，不使用最新版标签、不全局安装、不生成项目维护的上游依赖锁文件。第三方依赖及安装脚本按官方声明处理；新版 npm（包管理器）的脚本策略在此次独立安装中明确放行，旧版保持正常生命周期脚本行为。

安装缓存、临时文件与包管理配置均在工作区。安装进程及子进程由现有原生进程树管理；取消、网络错误和候选检查失败不会覆盖现用目录，缓存保留供重试。无准确下载总量时使用阶段进度。候选通过实际包版本、入口、网页、调度资源、插件适配与完整文件摘要校验后，才进入现有服务停止及事务替换流程。

下载采用 `prefer-offline`（优先使用缓存）策略，缓存缺失时仍正常联网补齐；不把普通模型下载的四通道限制套用到 npm（包管理器）安装，也不设置下载字节限速。版本、适配要求和工具配置共同决定候选目录标识，失败或取消保留该候选和工作区归档缓存。重试先核对目标与项目插件；完整候选按现有完整性缓存规则核验后直接复用，目标变化则使用另一候选。尚未完成或已损坏的候选不能直接启用，重新从经过 npm（包管理器）完整性核对的归档缓存解压，缺少的归档才下载。单个未下载完的归档由 npm（包管理器）重试获取，不承诺对该归档按字节断点续传；已完整缓存的其他包无需重头下载。

更新前先核对现用组件是否匹配目标来源、版本和适配要求，明确需要迁移时不再先完整读取旧组件。新候选完整摘要成功、前后文件指纹一致后生成独立复核记录；事务移动后再次核对文件清单摘要和指纹，再将结果交给启动校验缓存，避免紧接着重复读取全部文件。记录缺失、过期、内容变化或无法写入时，按原规则重新完整校验，不能绕过版本、插件适配、路径边界及安装绑定。界面显示依赖解析请求数、归档下载或缓存复用请求数、安装脚本和资源校验阶段，不将请求数冒充准确字节进度。

Windows（操作系统）缓存根路径按路径组件比较，兼容同一目录使用两种分隔符的写法，避免误判为缓存失效。后端启动盘点复用已经逐层拒绝链接的目录枚举结果，在精确文件集合匹配后逐文件核对类型和大小；必要入口仍检查路径边界，完整校验仍检查文件摘要，减少为每个依赖反复解析共同父目录的开销。

正式程序启动与服务重试检测 Node.js（脚本运行环境）的实际可执行性、版本、Windows x64（64 位系统）架构；安装和修复额外检测 npm（包管理器）。当前范围为 `^22.19.0 || >=24.0.0`（22 系列至少 22.19.0，或至少 24.0.0）。缺失时复用官方依赖引导；重新检测重新查找安装位置。pnpm（插件包管理器）随组件在工作区准备，由启动包装入口明确传给宿主。

启动直接运行已安装入口，保留桥接、动态端口、工作区配置、私有 Python（后端运行环境）搜索路径、正常退出和现有完整性校验缓存规则。安装清单记录实际文件完整性，不限定第三方依赖版本；清单同时登记到工作区组件绑定。

## 已安装组件与用户数据

安装新程序保留组件登记和用户数据。组件页展示 `installed_version`（已安装版本）、`version`（随包目标版本）、`update_available`（需要更新）及 `can_start`（允许启动）。判定依据是是否匹配本程序支持的目标组合；高于目标版本也需同步到目标版本。旧桌面包和旧物理包仍可诊断、导入和导出，导入后保留“需更新”门禁。

点击更新先准备候选，依赖不足先进入官方引导。通过完整检查后停服务并事务替换。成功刷新登记、启动上下文和校验缓存；只有全部必需组件就绪才恢复此前服务。失败或中断恢复旧文件，但旧组合仍不符合新程序时保持服务停止。

会话、凭据、任务、用户补丁及用户选择的插件位于用户数据目录，组件替换不会覆盖它们。配置档合并只更新程序管理的插件和默认项，旧依赖联接只有目标确认属于当前受管目录时才解除。

桌面 C++（编译语言）运行库来自独立的受信来源缓存 `desktop-crt`（桌面原生运行库），通过 `scripts/prepare-desktop-crt.py`（独立运行库准备脚本）核验；构建不再要求旧宿主安装器或旧运行清单。

## 验证入口

`tests/dsh-npm.test.mjs`（包安装适配测试）和 `tests/test_dsh_npm_distribution.py`（后端兼容、工具、完整性及导入导出测试）覆盖配置驱动版本与工具变化。原生公共模块测试覆盖精确兼容、旧来源迁移、组件事务、取消与启动门禁。`scripts/qualify-dsh-npm.py --workspace <目录>`（宿主隔离验收）核对已安装宿主及私有插件工具、两次实际网页启动、动态端口、项目桥接和正常退出；仅允许项目旁测试目录中的独立工作区。

宿主隔离验收要求工作区具备项目私有 Python（后端运行环境）；脚本先按正式程序流程准备配置档，并明确读取正式包的默认补丁，再调用插件工具，避免上游命令先生成空白配置档影响结果。

`scripts/qualify-unified-product.py`（正式程序隔离验收）继续核验安装器、统一程序包、首次管理页与保留数据重装。旧官方来源专项验收在新目标下检查迁移门禁。真实上游后续版本尚未适配时，以配置变化的隔离测试验证判定，不声称已验证未知版本的实际插件兼容性。
