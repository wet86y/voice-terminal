# 语音队列决策与后台问答策略

本文说明语音助手如何处理播报修订、取消和后台任务运行期间的新用户表达。系统提示定义位于 `voice_terminal/agent/prompts.py`（主提示文件）；请求上下文由 `voice_terminal/agent/context_builder.py`（上下文组装文件）生成。

## 语音队列修订与取消

- `speak`（新播报）只在输出队列空闲且存在尚未回答、仍有必要传达的内容时使用。活动队列已经覆盖用户表达时，应让现有播报继续。
- `revision`（尾巴修订）只能修改本轮仍可编辑的尾巴。只有新消息与播报存在实质不符，或需要补充尚未表达且确有必要的信息时，才启动修订。语气、措辞、标点、情绪和同义改写都不构成修订理由。
- 尾巴修订必须提交完整的新尾巴，并连同已锁定文本一起审计语义重复、事实、衔接、指代和必要要点。若轻微事实变化涉及已锁定文本，应在尾巴中简短说明变化并保留仍然有效的内容。
- 带文本的 `cancel`（取消并替换）用于锁定内容或回答前提与最新明确意图实质冲突的情况，主动撤销答非所问、失效前提或明显矛盾，不要求已经确认听到严重错误。锁定文本不代表已经听到；实际传达记录用于决定更正与衔接方式，不作为撤销失效待播音频的前提。替换只表达必要更正及回答，不重复已传达的有效信息。空文本取消只用于明确停止当前播报。
- 修订边界失效、队列忙碌、协议恢复或转写更新本身，都不能单独触发取消重讲。重新评估时，应结合最新意图、实际传达记录和队列状态。

整轮理解重点检查用户末尾的否定、转折、修正及最终要求，并保留前文的对象和有效条件；精修稿不因到达较晚就自动优先。当前计划仍成立则等待，仅可改尾巴变化则修订，锁定前提失效则取消替换。

取消声明完整校验后，服务同步撤销旧代次并启动音量收尾，新合成不等待旧服务清理。正常前300毫秒振幅由100%降到30%，随后200毫秒降到零；新音具备播放条件时，旧音最多再用30毫秒淡出，随后新音30毫秒淡入。替换过渡上限为600毫秒，与播放结束后的1秒尾巴续写窗口分别维护。降音量区间文字保守记录为传达不确定。

## 后台任务运行期间的用户表达

后台仍在运行不构成忽略用户表达的理由，也不意味着语音队列正在播放。收到用户的新问题、进度追问、呼叫或需要回应的闲聊时，应按当前已知信息回答；没有确认更新时，可以说明仍在处理或暂时无法确认，不能虚构进度、耗时、完成情况或结果。

只需对话回答且现有信息足够时，无需再次请求后台；`continue_listening`（继续倾听）仍可按需独立选择。不因问句包含“任务”“状态”或“进度”就再次请求后台。下列情况仍需通过 `request_shadow`（请求同一助手的后台执行）路由：

- 用户明确要求重新读取、刷新或核实；
- 需要实际执行文件、应用或外部资料操作；
- 用户补充、修改或撤销正在执行的意图；
- 用户回答了后台提出的必要问题。

若没有新用户表达且只收到重复的后台进度事件，应等待，不重答历史问题。若活动语音队列已经回答当前问题，也应等待原队列继续，不另起播报或取消。

## 提示注入位置与上下文契约

通用提示分别规定历史判断、动作路由和状态格式；具体队列决策核对以 `speech_queue_policy`（语音队列决策核对）作为请求末尾上下文条目，位于最终 JSON（结构化输出）约束之前。恢复提示、静默评估、唤醒确认和二等信箱评估仍须保留其场景信息，不能覆盖末尾的队列规则。

上下文组装、投影和裁剪须保留唯一一份 `speech_queue_policy`（语音队列决策核对）条目，并维持其请求末尾位置；最终输出约束仍紧随其后。相关行为由 `tests/test_context_cache_contract.py`（上下文缓存契约测试）和 `tests/test_json_schema_shadow.py`（输出结构与后台动作路由测试）覆盖。
