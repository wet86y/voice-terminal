# 分布式设备运行架构与开发顺序

## 广播网络许可与系统维护（2026-11-20，源码状态）

广播开关只控制公告、配对监听、项目网关及原生管理/文件入口。关闭广播保留设备配对、公钥和持久防火墙规则；系统 SSH（安全外壳协议）服务保持原状态，受限桥接继续拒绝广播关闭时的产品会话。再次开启先只读核对官方服务及三条项目规则，规则有效时直接复用，不申请管理员权限。

手动开启和自动发布共用系统准备入口。确认项目规则缺失、被禁用或不匹配时，才按需申请 UAC（用户账户控制）维护；无可用局域网、账户不支持或明确的组织策略限制直接报告原因。规则从 ActiveStore（当前生效策略存储）读取，修复后再次检查实际状态。自动维修失败或被取消后停止自动申请，等待用户在设备页主动重试；不以普通发现超时为依据重写系统配置。

首次需要系统修改时，由正式桌面程序自身启动系统维护宿主，本次运行复用该已授权进程。维护宿主只分派官方 SSH 准备、项目规则和受限公钥三类操作；命名管道拒绝远程连接，并核对双方实际进程编号。主程序退出导致管道关闭后，维护宿主结束。界面、插件和用户凭据不随维护进程提权。

设备公钥的强制命令绑定工作区、账户、设备和当前桥接协议，不绑定每次发布的构建编号。桥接仍校验正式入口文件摘要、当前发行身份和设备信任，并向本机服务报告实际运行构建。仅接受新授权格式；旧构建绑定命令不提供兼容入口，需要重新登记公钥一次。

PowerShell（脚本运行环境）按任务能力选择，优先用户通过 VOICE_POWERSHELL_PATH（解释器绝对路径）明确指定的版本；自动模式发现已安装的稳定 7 系列及系统 5.1，并在执行前验证签名、位数和所需模块。模块路径包含所选解释器自身及 Windows（操作系统）模块，不加载个人启动脚本。提权维护只使用标准受保护安装目录中的解释器，并在宿主中重新校验；执行失败后不切换版本重放写操作。

## 延迟本地计算、后台协作映射与控制台中继调研（2026-11-19，源码状态）

远程模式的首音延迟已改为项目已有的浏览器本地计时：不再映射服务端 `runtime.latency` 快照，也不使用服务端事件时间戳（两机时钟不同域）。本机模式仍使用同域时间戳校正；远程通道断开时显示“—”。验证见[远程模式首音延迟本地计算](../testing/remote-latency-local-20261119.md)。

远程模式“后台协作”面板的后台轨迹与待决审批已改为跟随服务端语音实时事件流（`runtime.snapshot`、`shadow.product`），不再只依赖打开页面时的一次性产品快照；实时通道未连接或尚未收到权威投影时回退到产品快照。授权按钮沿用既有远程固定操作 `dsh.approval.decide`，服务端仍按原审批编号和运行序号结算。验证见[远程后台轨迹与授权按钮映射](../testing/remote-shadow-approval-20261119.md)。

“后台协作”面板的服务端控制台入口仍未在客户端实现。调研结论：可用现有 SSH 固定桥接新增第五个标记和固定回环控制台中继实现，不需要放开 OpenSSH TCP 转发；令牌由服务端中继在首个文档请求中注入，客户端只转发本机回环随机端口。已完成 DSH 鉴权/同源规则核对和本机原始隧道、令牌注入探针验证，尚未实现、未做双机验收。设计、边界和风险见[远程 DSH 控制台中继（可行性调研与设计）](remote-dsh-console.md)。

## 媒体恢复与诊断修订（2026-11-19，源码状态）

媒体连接与一次监听输入分别管理。媒体协议第 2 版通过初始时钟请求的 `fields.runtime_controls`（运行期控制扩展说明）及客户端响应的 `runtime_controls`（是否支持扩展）协商能力；双方支持时，每 10 秒续测时钟，停止后重新开始使用新的 `capture_stream_id`（输入流编号），固定播放事务仍绑定原媒体连接。单次测量失败丢弃样本并重试，身份、租约、有效样本和连续音频约束继续保留。旧端不确认扩展时保留原协议行为，不向其发送新的运行期控制消息；长时恢复能力须两端同步更新。

远程界面的开始、停止统一调用 `voice.command`（设备绑定的管理命令），服务端核对本设备当前媒体输入；实时连接用于事件与字幕投影。命令结果区分 `completed`（完成）、`deferred`（已记住意图并延期）和 `failed`（未能执行）。短时管理探测失败保留既有转发连接最多 6 秒，期间不伪造管理可写状态；明确拒绝、主动断开、目标变化立即失效。语音接口存活和模型能力是否就绪分别呈现，能力恢复优先复用进程。

客户端增加有界滚动日志，双端记录媒体、输入、租约和恢复边界。源码修订与专项验证见[媒体恢复与日志验证](../testing/remote-device-recovery-20261119.md)。本节不代表已经覆盖本机或完成真实双机录放音验收。

## 客户端连接修订（2026-11-18）

最新客户端审计以本机实际安装 product-89ac31db0812c162（构建编号）为基线，保留此前服务端广播修订。当前本机已由用户切为 remote（远程模式），paired_host（配对服务端）为空；这表示尚未配对，不能显示“已配对服务端”或把本机缺少服务端模型判为失败。

本轮区分未配对、等待连接、暂停重连、管理连通、任务通道准备与核心能力失败；服务端 can_start（当前是否允许开始监听）不再用作能力就绪判据。管理租约申请在同一 SSH（安全远程连接）内复用，到期前换租约；仅在服务端声明 persistent_management（持续管理请求逐次核验信任）时复用通道。旧服务端仍逐次建立受限通道。只读轮询不占用写入幂等账本，写入仍校验请求编号和原参数。连续管理通道逐次核验当前构建、设备信任和自身会话代次。设备页面不另建自动重连计时器；主动断开先保存暂停意图。配对与连接纳入既有维护准入锁，回执重新核对工作区和设备配置。

本轮修订、证据及未验收边界见[客户端连接审计](../testing/remote-client-connection-20261118.md)。下方 product-54（旧构建）交付及阶段表是历史快照，不代表当前本机状态。

本轮最终已覆盖到 product-e920753e338e6b78（构建编号），原生、前端、SSH 回环及后端相关验证合计 695 项通过。正式窗口确认未配对等待、组件页无错误、模式选项可操作和离页返回状态一致；调试通道已关闭并正常重启。真实双设备配对、网络语音和长期运行仍不在本轮现场验收范围内。

## 已确认的产品边界

- 一套完整应用，逻辑上分为核心服务与设备执行两类职责。完整单机运行始终是一等模式，不依赖 SSH（安全外壳协议）、配对或其它设备在线。
- 第一阶段采用方案 A：多设备可同时在线，DSH（代理执行宿主）可以跨设备执行；同一主机同一时刻只允许一个活跃语音交互设备。
- 每个权威核心运行一套主语音控制器、会话台账及绑定该会话的 DSH 根代理。交互设备切换不新建另一套并行语音会话，不取消其它设备上已经启动的后台任务。
- 分开管理交互设备、执行设备、结果送达设备。任务发出后固定执行目标，设备离线不能把操作改投本机；新播报跟随当前交互设备，已有播放事务仍按原设备结算。
- 本地与远程使用相同的业务语义和结果约定；本地直接调用或采用 IPC（进程间通信），远程长期使用 SSH。无需让本地音频走网络序列化。
- 安装完整组件代表具备主机能力，与当前运行角色分开。运行角色包括独立运行、共享主机和连接远端主机；完整组件客户端可明确切回本机，运行中任务不自动跨主机迁移。
- 延迟第一、持续流式传输第二。上下行均保留原始 PCM（脉冲编码采样数据）和 Opus（低延迟有损音频编码）两档，默认 PCM。先以 PCM 建立双机基准，再实现 Opus；全面对照验收前压缩档标为实验功能。
- AEC（回声消除）跟随实际麦克风和扬声器所在设备。语音历史继续由权威主机维护，按设备实际输出证据结算。
- 桌面外壳、托盘、设备设置与配对属于本机；模型、主会话、历史及代理任务属于当前核心主机。客户端在线 TTS（语音合成）使用服务端凭据的临时授权，在客户端直接合成并播放，不把合成音频传回服务端。

## 职责与部署

| 层次 | 职责 | 本地与远程关系 |
| --- | --- | --- |
| 核心服务 | ASR（自动语音识别）、KWS（关键词唤醒）、VAD（语音活动检测）、情绪、事件、声纹、LLM（大语言模型）、语音调度、DSH、历史 | 每个权威会话一套，模型接收统一解码后的音频 |

| 设备执行 | 录音、播放、AEC、桌面观察与操作、文件、终端和本机后台进程 | 所在设备负责物理资源及释放 |

独立运行与共享主机都保留本机完整交互能力。远端交互占用语音会话时，本机仍是可执行目标；本机重新取得语音占用权，也应遵守同一切换流程。

轻量客户端只运行不依赖 Python（后端解释器）的本机外壳和设备层。客户端断线后保留管理与重连界面；未安装模型时不能宣称能够本机接管。完整组件客户端手动接管时启动自己的权威会话，原主机恢复连接后不自动合并两套会话。首版从界面手动切换交互设备，未活跃设备不持续上传麦克风。

| `sequence`、`start_sample`、`sample_count`、`discontinuity_before` | 消息序号、首采样位置、采样数及本帧前的采集缺口标识，用于去重、连续性恢复与长度检查 |
| `sample_rate`、`channels`、`sample_format`、`codec` | 采样率、声道数、采样格式、传输编码；上下行分别协商 |
| `request_id`、`task_id` | 请求编号与任务编号；重复请求核对原结果，不盲目再次执行 |
| `execution_device_id`、`delivery_device_id` | 执行目标在任务派发时冻结；送达目标在播放事务分配时确定，新播报跟随当前交互设备 |
| `playback_key`、`receipt_sequence` | 播放事务标识与回执序号；绑定输出设备及流代次，避免旧回执覆盖新事务 |

已有 `input_owner`（输入处理所有者）表示 KWS、ASR 等链路内部所有权，不能改作活跃设备字段。已有轮次 `generation`（输出代次）也不能兼作连接或设备占用代次。

本地接口应覆盖现有启动、停止、读帧、诊断、前处理、播放器控制和输出快照语义。远程停止与快照需要等待设备确认；当前同步调用不能在适配器内阻塞事件循环，也不能在命令发出时就伪造“停止成功”。实施时应将远程命令受理、确认、超时和最后可信快照显式接入输出结算。

## 音频与实际输出契约

### 输入与前处理

- 上行为 16 kHz（每秒一万六千采样）、单声道、16 位有符号 PCM；二进制流明确字节序，默认约 20 毫秒一块，即 320 个采样、640 字节，原始采样负载约 256 kbps（每秒千比特），另计协议开销。
- 两档都持续传输环境声音，不以客户端 VAD 决定是否上传。Opus 在主机按同一流有状态解码一次，再供识别和分析共享；模型窗口由现有分析层累积。
- 网络队列有界，记录积压及最老音频年龄，不增加等待完整句子的缓冲。溢出、缺口、重连、编码切换应显式结束旧流并恢复输入状态，不补造采样连续性。
- `captured_at`（采集单调时间）当前参与打断、轮次时限与输出位置判断。不同机器的单调时钟无共同起点；保留设备采样时钟和接收时刻，在适配层建立有误差记录的主机时间映射，不直接复制远端时间，也不把每块到达时间当作采集时间。失去可信映射时重建流或降低判断精度。
- AEC 使用同设备实际输出的参考，保持现有 10 毫秒处理粒度。远端不仅返回处理后的 PCM，还必须提供处理健康、近端人声判定及与音频对齐的状态；否则现有受保护打断与失效恢复规则无法复用。主机不能通过简单禁用处理器来宣称远端 AEC 健康。
- 两路远端播放都将设备端和在途音频储备限制为 400 毫秒，为 500 毫秒 AEC（声学回声消除）延迟保护上限留出余量。设备每个采集帧都用当前播放快照更新参考延迟；快照读取失败时撤销受保护打断资格。客户端直放等待储备释放期间继续上报设备时钟进度，使已播音频及时退出缓冲估算。
- 客户端直放与设备下行共用按 `playback_key`（固定播放事务编号）停止并读取快照的处理。终态回执按原播放键保存，迟到的合成取消复用原停止结果，不停止后续播放；无输出的直放事务也会先取消合成生产，再结算原生设备停止结果。
- 无损档指传输不额外损失已处理采样，并不跳过 AEC 或降噪。有损档解码后格式相同，不保证 ASR、情绪、声纹和事件结果与原音一致。

### 下行、打断与台账

下行默认由主机合成，再流式发送到交互设备。**上行的 16 kHz 约定不能套用到下行。** 当前在线合成为 32 kHz，本地播放器支持 16、24、32、48 kHz；应按合成与设备能力协商并同步反向参考时钟，不能为了统一传输而静默降低全部播放采样率。

设备回执至少覆盖开始实际输出、累计提交位置、实际输出估计、暂停、恢复、欠载、取消、替换及最终停止快照，并报告 `precision`（证据精度）。当前本地 `played_ms`（回调提交时长）与 `output_estimated_ms`（设备实际输出估计时长）存在明确区别；远端同样不能把“已接收”或“已入队”当作“用户已听到”，也不能承诺超出硬件回调与时间估计的测量精度。

主机只按最后可信证据提交传达文本。断线后的输出状态保留不确定性，恢复连接先核对原事务，不重播已经输出的内容。设备端 AEC 和播放停止等本地控制不得依赖一个往返完成后才能保护麦克风；主机仍拥有最终语音事务与台账结算权。

### 活跃交互设备切换

1. 主机串行处理切换，停止接受旧设备的新输入，撤销旧占用代次。
2. 结束旧输入流，按现有输入边界结算或取消未完成片段，清除旧音频及识别流缓存；保留主会话历史和 DSH 根代理。
3. 正在输出的事务仍绑定原设备，取得停止或完成回执后结算；无法确认时标为不确定，不把剩余音频直接投给新设备。
4. 向新设备授予新的占用代次和音频流编号，收到就绪确认后接受语音输入。旧设备迟到消息与回执只能进入各自原事务。
5. 已派发后台任务继续绑定各自的执行设备与既定送达规则，不因切换而取消、迁移或重做。

连接恢复只恢复设备可达性，不恢复旧占用权。设备切换、语音输入停止与会话重置应分别定义；不能复用 `session.reset`（会话重置）来清除整个核心历史。

## SSH、设备执行与权限

局域网通过 mDNS（多播服务发现）辅助发现；异地使用保存的地址或 Tailscale（组网工具）地址。客户端主动通过 SSH 连接共享主机，客户端无需开放 SSH 入站；主机通过双向业务通道派发设备任务。发现结果不代表设备已获信任，手动地址也必须走身份核对。配对绑定稳定设备身份、SSH 主机指纹与公钥；指纹变化不得无提示续连。

控制、音频和大文件传输分离。实时音频使用独立 SSH 连接，播报控制任务与截图、文件等普通设备任务独立轮询。内部业务服务保持回环监听，通过受限入口和隧道访问。现有语音接口不能仅因位于 SSH 转发后，就把任意本机进程视为已授权客户端；远端身份、业务授权、浏览器来源和设备操作权限都要核验，不能直接把旧管理接口暴露到局域网。

### 高频截图与文件附件

远端截图任务通过控制通道传递截图范围和文件票据，原始双图经独立 FILE（设备文件通道）上传。服务端验证文件和裁剪范围后，用原始图片向 DSH（代理执行宿主）交付。按需截图的回环响应依次包含四字节大端清单长度、JSON（结构化文本）截图清单、全局图和局部图。读取已登记的会话图片时，回环响应直接返回单张图片字节。DSH 校验摘要后按内容复用附件引用，工具结果只携带视图信息与附件引用。

已暂存的设备文件通过 `read_stream`（一次打开原始文件流）交给 DSH。服务端为同一个已复核的暂存文件持有读句柄，逐段读取并在完成、取消或断开时释放句柄和票据。流绑定当前 DSH 激活与原设备连接代次，DSH 在入库前验证整份文件的长度和 SHA-256（内容摘要）。文件内容由一条回环请求交付，业务接口继续负责配对、操作授权与设备选择。

以上回环附件接口随服务端与 DSH 插件同步切换。设备间仍使用现有受限 SSH（安全外壳协议）和 FILE 通道。本阶段的优化覆盖服务端向 DSH 的附件交付。设备间每次建连和分块确认的耗时，以及附件与语音并发时的表现，由双机实测评估。

实现见[服务端附件传输](../../voice_terminal/server/dsh_attachment_transport.py)与[DSH 附件读取](../../integrations/dsh/voice-terminal/src/shared/attachment-transport.ts)。

### 远端桌面执行器

社区 [dsh-windows-remote-ssh（远端 Windows 操作插件）](https://github.com/pureexe/dsh-windows-remote-ssh)可作为复用来源。2026-11-14 核对其[说明](https://github.com/pureexe/dsh-windows-remote-ssh/blob/main/README.md)与[包声明](https://github.com/pureexe/dsh-windows-remote-ssh/blob/main/package.json)：现有方式通过 SFTP 投放辅助脚本及请求，再以一次性计划任务进入已登录的交互桌面；它不是常驻音频执行器。开发依赖基线为 DSH 0.1.5-rc.2，同级依赖范围虽允许更高版本，也不能据此认定已兼容本项目 0.2.1-rc.5。接入前固定不可变提交、核对 MIT（宽松开源许可证）声明、工具接口、审批与附件，再决定复用范围。

固定上游提交及基线摘要见 [远端插件上游锁](../../config/dsh/remote-ssh-upstream.lock.json)。Windows（操作系统）的 SSH 服务会话与用户交互桌面分离，不能直接在服务会话中执行截图、录音或键鼠并期待访问用户桌面。产品改造需与已登录用户会话中的常驻执行器通信；锁屏、无人登录、会话切换和权限不足都要明确返回能力不可用。

固定上游提交已登记，原始基线测试通过。派生 DSH（代理执行宿主）device-control（设备控制）组件现已通过桥接回调连接统一设备路由：根代理可列出设备、读取固定设备窗口清单及有界观察、经一次性审批复核后提交动作，并查询原任务；终端与文件能力也已连接固定执行设备及任务/附件通道。窗口或执行器代次变化、未授权、断线和未知回执均不会改投本机或自动重发。阶段 4 本机类型检查、正式构建和 116 项测试通过；最新客户端通过远端正式包校验。仍缺从获准交互客户端真实配对，并由 DSH 工具执行远端观察、文件、终端或桌面动作及核对原任务回执。原上游逐请求 SFTP 临时脚本投放和计划任务执行不进入产品运行链路。

本地 DSH 原生命令与文件工具继续使用本机环境；远端操作显式选择已授权设备。审批绑定设备、任务及操作，桌面观察也绑定设备和观察代次，防止基于 B 的旧截图向 C 执行动作。断线后结果未知的有副作用操作先查询原任务，不自动重发，也不改投本机。

### 配对信任状态

`data/state/device-trust.json`（设备信任登记）只记录已批准设备的公开身份，格式版本为 `schema_version: 1`。遇到未知版本、重复字段、摘要或路径异常时保留原件并拒绝配对写入；不得静默重置该文件。

| 字段 | 中文说明 |
| --- | --- |
| `schema_version` | 设备信任登记格式版本 |
| `devices` | 已批准或已撤销设备记录 |
| `device_id` | 稳定设备编号 |
| `public_key` | OpenSSH Ed25519 公钥；不包含私钥 |
| `fingerprint` | 公钥的 SHA-256 指纹 |
| `state` | `trusted`（可信）或 `revoked`（已撤销） |
| `trusted_at_ms` | 首次明确批准时间，Unix 毫秒 |
| `revoked_at_ms` | 撤销时间；仍可信时为空值 |

配对码以摘要形式暂存于主机进程内存，待批准请求及客户端随机数也只保存在内存；关闭配对窗口或重启即清除，只有主机明确批准才将公钥写入信任登记。当前代码已有受管 `authorized_keys`（授权公钥清单）更新脚本、SID（安全标识符）及公钥文件 ACL（访问控制列表）检查、固定来源范围和受限命令；配对后的普通请求也校验固定目标与设备信任。上述代码尚未通过真实 Windows 账户、公钥文件权限或 OpenSSH 登录行为验收；客户端签名申请仍要求 SSH 登录密钥已能通过系统 SSH 账户验证。

共享主机的 OpenSSH（开放安全外壳组件）检查、安装及修复应纳入正式程序的组件管理任务；客户端无需 SSH 入站服务。系统安装可能需要管理员授权并可能受系统策略限制，实施时展示具体范围和失败原因；分发器不安装组件，普通单机启动不安装或开启 SSH。轻量客户端的原生音频依赖也遵守相同组件边界。

每步先保持现有单机契约，再增加该步的新能力。阶段 0 固定 DSH（代理执行宿主）上游原始仓库及测试基线；阶段 1 仅收拢本地接口，不建立并行语音会话，不添加未经兼容组件管理的运行时设置迁移。
