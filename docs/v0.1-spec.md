# 本地模块化实时语音终端 v0.1 当前边界

> 历史设计文档：以下“仅包含前端、后端未实现”和“贾维斯”唤醒词描述已过时。仓库现已包含真实后端，默认关闭唤醒，可选关键词为 hei claw。后续目标见 [v0.2](v0.2-spec.md)。

这份文档根据“分析语音电脑方案”会话整理，作为 v0.1 前端与后端的共同开发边界。

## 唯一目标

在 Dell G15（i7-13650HX + RTX 4060 Laptop 8GB）上验证一条可以测量延迟的中文实时语音对话链路：

```text
待机监听 → “贾维斯” → 收听 → 流式 ASR → 判断说完
→ 流式 LLM → 文本流整形 → 流式 MiniMax TTS → 播放
```

v0.1 的重点是低延迟、模块可替换、故障可见、支持取消，以及网页只做控制台而不成为语音主链路的依赖。

## 组件边界

| 能力 | v0.1 方案 | 运行位置 |
| --- | --- | --- |
| 唤醒词 | sherpa-onnx KWS，关键词“贾维斯” | Windows CPU |
| 讲话检测 | FSMN-VAD + 静音时间规则 | Windows CPU |
| 实时识别 | Paraformer-zh-streaming | CPU/CUDA 可配置 |
| 文本生成 | OpenAI-compatible streaming Provider | 云端 |
| 语音合成 | MiniMax WebSocket TTS Provider | 云端 |
| 控制台 | Vue 3 + Vite + WebSocket | 浏览器 |

第一版不把 ct-punc、SoulX、本地 TTS、OpenClaw、数据库、RAG、AEC、Electron 等加入主链，除非它们成为解决当前主链阻塞问题的必要条件。

## 运行结构

```text
浏览器 Web Console
        │ localhost WebSocket
        ▼
Windows Voice Server
  ├─ Audio Capture / Playback
  ├─ KWS / VAD
  ├─ Voice Controller
  ├─ LLM / TTS Client
  └─ Latency + Logs
        │ localhost WebSocket
        ▼
独立 ASR Worker（Paraformer）
```

麦克风和扬声器由 Windows 管理。ASR 使用独立 Worker，方便在 Windows 原生与 WSL 之间切换，并允许单独重启。

## Controller 状态

```text
STARTING      启动中
IDLE          等待唤醒
LISTENING     正在听用户
FINALIZING    确认这一轮语音结束
THINKING      等待 LLM 首字
SPEAKING      AI 正在讲话
INTERRUPTING  正在取消当前回答
ERROR         异常
```

KWS、VAD、ASR、LLM、TTS 和播放器全部由后端编排。前端只发送启动/停止会话命令，不能自行推进这些状态。

## 前端控制台边界

前端只有一个操作按钮：

```text
开始说话 → session.start → 后端持续监听
停止监听 → session.stop  → 后端停止监听
```

页面加载后自动连接 Voice Server。连接失败时显示错误并禁用按钮，不提供演示模式、实时模式、连接按钮、重试按钮、麦克风测试按钮或 TTS 测试按钮。

前端只展示后端提供的：

- Audio、KWS、ASR、LLM、TTS 服务状态。
- 当前状态和当前 Turn ID。
- 用户语音的 partial/final 转录。
- LLM 流式回复。
- TTS 等待文本、TTS 状态和音频缓冲。
- 当前轮完整延迟节点。
- 最近 10 轮转录、回复和延迟摘要。
- 后端错误。

浏览器不调用 `getUserMedia`，不采集 PCM，不运行本地模型，也不计算延迟。所有延迟值必须由 Voice Server 直接发送。

## 当前仓库已实现的前端范围

当前仓库已经完成控制台和协议适配层，未包含 Voice Server 或任何真实模型进程。实现边界如下：

| 范围 | 当前行为 |
| --- | --- |
| 连接 | 页面挂载后自动连接配置中的 WebSocket；失败后显示错误并保持离线，不自动重连 |
| 控制 | 一个按钮发送 `session.start` / `session.stop`；状态以服务端事件为准，不做乐观更新 |
| 监控 | 展示运行时快照、Audio/KWS/ASR/LLM/TTS 服务状态、当前轮文本、TTS 缓冲和后端延迟 |
| 路由 | 按连接内 `seq` 丢弃重复/乱序消息，按当前 `turn_id` 丢弃旧轮迟到事件 |
| 历史 | 只接受 `turn.completed`，最多保留最近 10 轮 |
| 故障 | 展示后端 `error`，不创建替代状态、假数据或本地指标 |

这意味着前端联调的最小可用后端不是“能接受按钮消息”即可，而是必须能先推送真实的 `runtime.snapshot`，并持续按照 [WebSocket 协议](websocket-protocol.md)提供状态和轮次事件。

## 前后端联调验收顺序

建议按下面的顺序接入，便于区分连接问题、状态问题和语音链路问题：

1. 仅启动 WebSocket，验证页面自动发送 `subscribe`，并能用 `runtime.snapshot` 初始化页面。
2. 返回 `can_start: true`，验证按钮可用；点击后只验证收到 `session.start`，页面不会自行变成 `LISTENING`。
3. 推送带新 `turn_id` 的 `session.state`，验证当前轮被创建并显示后端真实状态。
4. 依次推送 partial、final、assistant delta、TTS 和 latency 事件，验证替换、拼接、只读展示与 `null → —` 映射。
5. 推送 `turn.completed`，验证记录进入历史；连续完成 11 轮后只保留最新 10 轮。
6. 注入重复/低序号消息和旧 `turn_id` 消息，验证它们不会覆盖当前页面。
7. 推送 `error` 或关闭连接，验证错误可见且启动按钮禁用；刷新页面后才重新尝试连接。

前端验收不依赖麦克风权限、浏览器音频输入或本地时间差。真实音频采集、播放、模型状态和延迟测量必须在 Voice Server 中单独验收。

## 必须保留的后端机制

- 每轮对话都有唯一 `turn_id`，例如 `turn_000021`。
- 唤醒前保留 1–2 秒内存 Ring Buffer，避免“贾维斯 + 后续指令”丢字。
- TTS 与播放器之间有短音频队列，网络抖动不能直接造成播放断裂。
- LLM → TTS 经过 Text Stream Bridge，按后端策略分段。
- LLM、TTS、播放器必须有取消接口；新轮次结果不能污染旧轮次。
- 默认不保存全天麦克风原始音频，只在显式打开 Debug Audio Capture 时保存。

## 延迟指标

后端逐步计算并通过 `latency.snapshot` 推送以下节点：

```text
wake_detection_ms
asr_first_text_ms
speech_end_confirmation_ms
llm_first_token_ms
llm_request_to_first_tts_text_ms
tts_text_to_first_audio_ms
first_audio_to_playback_ms
speech_end_to_playback_ms
turn_total_ms
```

前端只显示后端发来的数值；`null` 显示为 `—`，不替换为零，不使用本地时间戳推导。
