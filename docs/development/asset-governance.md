# 开发资产治理与覆盖更新

本项目是开发仓库。Git（版本管理）保存源码、依赖锁、测试与小型固定种子；`.local`（本机资源目录）保存当前程序、运行环境、模型、工具、持久数据及可再生成产物。日常修订不生成另一套安装环境，也不按版本复制工作区。

机器可执行规则位于 `config/development-assets.json`（开发资产策略）。根 `AGENTS.md`（项目级代理指令）仅保留项目原则、数据保护边界和按需文档入口；具体工具、参数与维护步骤以本文及对应脚本为准。本规范同时处理提交历史增长和本机磁盘增长，两者不能用同一个大小指标衡量。
本文记录资产管理的当前实现和适用流程，涉及资产收录、现场保留或回收时按需查阅；具体实现类、命令和预算不自动成为所有开发任务的前置条件。简单代码修订不要求先安装钩子或运行容量审计。

## 借鉴与选择

- Git（版本管理）的忽略规则只影响未跟踪文件，不阻止强制加入，也不处理已跟踪文件，因此保留 `.gitignore` 并增加提交前的暂存对象检查。参见 [Git 忽略规则](https://git-scm.com/docs/gitignore)。
- 大资产保留来源、版本、许可证及摘要，把内容放到发布资产或独立存储。GitHub（代码托管平台）也建议通过发布入口分发大型二进制，避免将其反复写入提交历史。参见 [大型文件管理](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)。
- DVC（数据版本管理工具）通过元数据与外部存储管理数据及模型。当前项目已有 `config/resources/catalog.json`（资源目录）、依赖锁和完整性清单，先复用这些能力，不再增加第二套模型缓存和元数据权威。未来有多人协作训练数据或自有模型版本需求时，再评估 DVC 或 Git LFS（大文件指针存储）。参见 [DVC 外部存储](https://doc.dvc.org/user-guide/data-management/remote-storage)。
- Cargo（原生包管理器）按构建配置保存最终和中间产物。目录固定不能保证容量固定，因此保留共享构建缓存、按配置测量，不在每次开发时自动清空。参见 [Cargo 构建缓存](https://doc.rust-lang.org/cargo/reference/build-cache.html)。
- 生成物附带足够的输入、工具链和摘要，才能从源码核对产物；构建信息应作为独立产物，不夹进业务源码或长期复制大目录。参见 [记录可复现构建环境](https://reproducible-builds.org/docs/recording/)。这套治理不声称当前全部二进制已实现逐字节可复现构建。

## 资产归属与生命周期

| 分类 | 权威位置 | 后续行为 |
| --- | --- | --- |
| 源码、测试、依赖锁、当前文档 | 仓库跟踪目录 | 用提交保留修订；不复制整树做旧版备份 |
| 当前程序本体 | `.local/app` | 校验候选、事务换入、成功回收旧本体，固定位置覆盖 |
| 运行环境、模型、工具 | `.local/runtimes`、`models`、`tools` | 由组件管理与锁控制更新；普通代码发布复用 |
| 用户数据与滚动备份 | `.local/data`、`backups/user-data` | 持久保存，不能按缓存策略处理 |
| 原生构建缓存 | `.local/build/desktop/product` | 调试、正式优化分项预算告警，手动选择维护时机 |
| 当前程序包与安装器 | 固定构建及交付路径 | 覆盖同名输出；只有明确交付才生成安装器或整包 |
| 已接入的验证任务 | `.local/tmp/tasks/<类型短码>/<短任务标识>` | 成功回收；已结束失败现场有限保留；中断现场保守留存 |
| 验证摘要 | `.local/cache/reports` | 默认固定文件覆盖；不复制环境、模型或大构建目录 |
| 包下载及构建依赖缓存 | `.local/cache` | 只读预算审计；由各包管理器或具体维护动作处理 |

## 修订、调试与更新流程

1. 修改前查看 `git status`（版本状态），确认并保留其他会话正在修改的内容。
2. 日常运行 `npm run dev`（业务源码开发）：复用当前程序和组件，只切换源码与前端输入。界面演示运行 `npm run dev:ui`（独立演示），按需构建演示宿主。
3. 完成改动后运行对应回归；没有新增修改或新发现时，不重复跑重型模型验证。测试失败先定位原因，不删除回归资产来消除失败。
4. 需要将代码更新到本机正式程序时运行 `npm run desktop:publish`（本地覆盖发布）。默认只构建正式优化版本；原生演示宿主需要同步重建时，显式运行 `scripts/publish-desktop.ps1 -BuildDemo`（同时构建演示）。`-SkipBuild`（复用已构建产物）与 `-BuildDemo` 不应同时使用。
5. 只有明确交付时使用现有分发入口生成固定安装器。同时更新本机和分发使用 `npm run desktop:deliver`（同包交付）；同时公开发行使用 `npm run github:release:local`（本机与发行组合），不串行重复运行默认完整流程。具体入口及复用规则见[开发、构建与同包交付流程](desktop-pipeline.md)。日常调试不要求安装器、模型离线整包或历史版本目录。
6. 提交前审查差异和暂存内容，运行 `npm run assets:check`（资产提交检查）。不要自动暂存整个工作区，不自动改写版本历史。

当前发布事务已经支持失败恢复与固定目录换入。本次治理维持这一语义，并将程序包组装目录的删除改为不跟随重解析点的安全删除函数。

## 提交检查

```powershell
npm run assets:hook       # 本机启用提交前资产检查；已有自定义钩子时拒绝覆盖
npm run assets:check      # 显式检查暂存内容，不执行暂存或提交
```

规则检查 Git（版本管理）暂存对象，不会用未暂存的小文件替代已经暂存的大内容。采用同一提交的暂存策略，资源、摘要、许可证说明和策略可以一次原子修订，不要求拆成两次提交。未暂存的放宽规则不影响检查。禁止删除开发入口依赖的策略文件，禁止生成目录、被忽略文件、本机环境配置，以及普通源码路径中的模型、压缩包和编译产物进入提交。固定的 `tests/fixtures`（测试输入）与前端资源目录允许有意收录的小型二进制，不按后缀一概拒绝。

普通文件 1 MiB（兆二进制字节）、一次提交不同内容对象总量 5 MiB 是建议值，默认只提示，不阻止合理重构或资源更新。总量按完整对象计算，不是差异文本大小，因此不能单凭这个数字判定提交不合理。只有显式执行 `npm run assets:check -- --strict`（严格检查）才让这些提示返回失败；本地提交钩子不启用严格模式。删除旧生成物仍允许。

既有三个超限资源以精确路径、SHA-256（内容摘要）及用途登记：原生语音补丁、语音检测种子、离线分词器。它们是现有安装闭包的一部分，此次不迁移或重写历史。摘要匹配的内容免去重复大小提示；变化时提醒共同审查资源目录、许可证与新摘要。资源自身的完整性仍由构建、安装和资源校验负责，不把开发策略变成第二套强制资源清单。原生补丁目前约 40.7 MiB，是后续减少二进制提交增长的重点。

钩子依赖本地配置，需要自动提交检查的新检出可按需执行安装命令；未安装钩子不影响启动、调试或显式检查。主仓库和关联工作树共享部分版本配置；旧分支或工作树缺少治理文件、解释器或检查环境不可用时，钩子提示后继续正常提交，避免环境修复反过来依赖治理工具。显式检查命令仍以退出码 2 报告工具不可用，不伪装为检查通过。Git（版本管理）允许跳过本地钩子，自动化合并验收仍需显式运行检查；它是防误提交工具，不是安全边界。

## 测试与诊断任务

新增会保留现场的验证工具，可使用 `scripts.workspace_assets.ManagedRun`（受管验证任务），或具备同等保护的现有工具。在测试父进程中创建目录，不让每个子进程再创建一套现场：

```python
from scripts.workspace_assets import ManagedRun

with ManagedRun('feature-check') as run:  # feature-check（专项验证任务）
    output = run.path / 'result.json'     # output（本轮输出文件）
    # 使用本轮目录验证；退出前等待所属子进程、数据库和文件句柄关闭。
```

当前接入后端测试、更新交接验收及语音设计验证。成功后删除本轮目录，仅覆盖写固定小摘要；语音设计成功记录样音摘要，不留下指向已回收音频的失效路径。更新交接验收的详细成功摘要固定为 `.local/cache/reports/app-update-handoff-latest.json`。
需要人工听音时，为语音验证追加 `--keep-artifacts`（保留成功样音），或在受管任务中设置 `keep_success=True`（保留成功现场）；这类现场仍按已结束现场的数量、期限和容量处理。登记、旧现场维护、摘要写入或收尾删除失败只提示并保留文件，不能把已通过测试改成失败，也不能覆盖原始断言异常。任务输出目录越界或祖先重解析点仍然拒绝；无法在安全目录写入测试输出是实际环境故障，不伪装为成功。

正常结束的失败现场按任务类型保留：最多两轮、最长七天、合计最多 512 MiB。下一次受管任务或显式维护时回收超限现场。最新失败大于预算时，也不能无限保留；小型任务摘要仍保留。进程仍存活、身份无法确认、清单损坏、未知目录均跳过。强制中断或异步取消不能证明所属子进程已退出，保持“运行中”登记，留待人工核对，不自动将其改成可删除失败现场。
普通新任务只维护同类旧现场，不扫描其他类型；完整跨类型维护通过显式命令执行。物理目录使用短码：`b`（后端测试）、`u`（更新交接）、`v`（音色设计），完整类型名仍存登记和摘要；后端测试的夹具与临时目录分别使用 `p`、`s`（测试夹具、进程临时文件）。任务标识以独立创建和碰撞重试保证不覆盖并行任务。已存在的长目录仍可被显式维护识别，不迁移或删除正在使用的旧现场。

```powershell
npm run assets:prune                 # 仅列登记现场候选
npm run assets:prune -- --apply      # 执行候选回收；现用资源和未知目录不参与
```

自动回收只作用于新登记的任务，不能识别的历史恢复目录、旧报告、仓库外验收副本不追溯删除。资源下载和外部资格验收尚未全部接入此生命周期；新增会保留现场的验证工具应复用现有任务管理，或提供同等隔离、登记及安全回收机制，无须让每个单元测试直接引用指定实现类。旧入口按维护范围逐步迁移，不把整个 `.local/tmp`（暂存父目录）当成一个任务。

## 本机预算与构建维护

```powershell
npm run assets:audit                 # 固定分项只读预算审计
npm run assets:audit -- --strict     # 超限返回失败，便于维护或自动化验收
```

初始告警线：原生调试缓存 16 GiB、正式优化缓存 10 GiB、报告 1 GiB、共享包缓存 3 GiB、全部暂存 4 GiB。预算依据当前快照设置，后续根据真实开发周期调整并记录理由；它们不是自动删除上限。容量扫描仅在显式维护命令运行，普通启动、热更新和原生构建不扫描磁盘、不增加治理前置条件。

容量按普通文件路径累计，目录联接不遍历，硬链接可能重复计数，不能把告警体积等同于可释放空间。最新报告覆盖写 `.local/cache/acceptance/asset-budget.json`。本次初始审计能发现已有调试缓存超限，没有假装旧缓存已经缩小。

原生缓存维护先停止使用该缓存的构建、测试或演示实例，再核对具体构建配置和工具链。优先消除重复构建配置与来源差异，再选择具体缓存清理，不在构建失败后的每次重试自动清整个目录。官方 [Cargo 清理命令](https://doc.rust-lang.org/cargo/commands/cargo-clean.html) 支持按构建配置清理，但在此工作区执行前仍必须检查目录及重解析点，不能将其当成可绕过工程删除边界的入口。

持续观察预算报告与任务保留数量即可，不再按每轮验证复制大目录保存“证据”。模型、运行环境、数据与开发工具不参与此预算回收，既有事故恢复候选须另行核对后处理。

## 开发影响复核

| 工作流 | 现行影响 | 保留的边界 |
| --- | --- | --- |
| 源码业务开发、前端热更新 | 原启动脚本未接入治理，不增加扫描、构建、模型加载或网络请求 | 既有单实例和业务完整性校验不变 |
| 界面演示 | 仍由原入口按需构建调试宿主；不要求先发布正式程序 | 固定原生缓存与隔离业务边界不变 |
| 原生构建 | 已撤回自动预算扫描，成功结果不依赖治理文件或报告写入 | 既有编译、来源锁和参数校验保留 |
| 正式覆盖发布 | 默认少一次调试宿主编译，仍组装当前正式包并事务覆盖；无需生成对外安装器 | 既有停机、候选校验与失败回滚保留 |
| 正常提交 | 大小与资源摘要默认提示；暂存策略和资产可同提交；批量查询对象大小减少逐文件进程开销 | 明确生成物、环境配置与不受管录音仍阻止 |
| 后端测试 | 多一个小型任务登记与有限现场维护，无新增第三方包；收尾失败不改测试结果 | 活动现场和未知目录不删除，实际测试断言原样保留 |
| 人工听音排查 | 可显式保留成功样音，不被迫重跑生成 | 受控目录和有限保留规则仍适用 |

这些结论以源码接线、隔离场景和回归测试为依据；本轮不为证明治理而重建原生依赖或请求真实模型，不承诺所有硬件上的固定耗时。

全量验证曾实际发现初版长任务目录导致 11 项 Windows（操作系统）路径长度错误。修复采用更短物理目录，不改业务源码、不改系统长路径设置、不放宽断言；相关 93 项定向回归随后通过。后端测试路径前缀已有长度回归，避免只验证治理自身而遗漏深层业务路径。

缩短路径后的全量后端验证为 **1718 项通过、3 项跳过、7 条第三方弃用警告**，耗时约 152 秒；最后新增的一项“治理脚本语法损坏也不阻止正常提交”用例单独通过。前端开发入口 3 项回归、原生启动与发布参数检查通过。以 `d964298`（验证时的源码基线）为参照，本轮治理没有修改业务源码、前端代码、业务启动脚本与原生构建脚本。

本机一次隔离测量中，101 个暂存文件的批量检查约 0.37 秒；100 个小源码文件的完整带钩子提交约 0.76 秒，包含解释器探测；本仓库空暂存区完整命令约 0.45 秒。首次无钩子提交约 0.12 秒，但首次和修改提交输入不同，不能把两者差值作为严格性能对照。数据保存在 `.local/cache/acceptance/asset-impact.json`（开发影响摘要），不作为其他硬件或大二进制更新的耗时保证。

仍保留的取舍：工具不可用时，本地钩子提示后放行，因此该次防误提交检查没有实际执行；显式检查会返回工具不可用状态供维护。真正输出目录不可写、祖先是重解析点等环境问题仍会拒绝测试，防止再次穿透共享资源。历史构建缓存、外部手工验收、未确认结束的中断现场不自动清退，不承诺在保持开发缓存的同时把所有目录强制压到预算内。
