# 更新日志填写规范

本规范适用于后续程序本机更新、分发交付及 GitHub（代码托管平台）发行。每个版本只维护 `docs/releases/v版本号.md`（对应版本更新文档），GitHub 发行正文与程序内“本次更新”使用这同一份内容。

## 对照范围

编写前，先确认上一次实际更新的程序，再对照本次准备更新的本地程序，梳理两者之间的完整变化。通过交付记录中的版本、构建编号及对应源码确认起点与终点；同版本再次更新也要区分实际构建。

- Git（版本控制）记录只用于辅助核对完整差异，不能用最近几次提交、当天提交或当前任务的修改代替整个更新区间。
- 包含本轮实际交付、但尚未提交的本地改动；尚未进入本轮程序的改动不写入。
- 本机更新以上一次成功的本机更新为起点；对外发行以上一次对外更新为起点。本机已更新但尚未公开的用户可感知变化，在对外发行时仍需合并保留，不能只写最后一次本机更新的增量。
- 对照依据记在 `docs/releases/current-release.md`（当前交付记录）或对应内部交付记录中，不放进用户更新日志。无法确认起点时先查明，不凭少量提交推测或宣称已经覆盖完整变化。

## 固定正文

除产品与版本标题外，正文只保留以下三个部分，名称和顺序固定：

1. **新增与改进**：新增能力、操作体验改善及用户能感知的行为变化。
2. **修复**：用户遇到的问题、出现的场景及修复后的结果。
3. **升级注意**：升级需要执行的操作、首次启动可能出现的等待、设置与资料变化，以及影响使用的限制。

三个部分都保留。没有新增或修复时填“无。”；确认不需要额外操作时，升级注意填“无需额外操作。”。不要为凑内容重复已有功能，或添加未经确认的数据保留、兼容性和性能承诺。

每条尽量用一到两句话，只说清楚用户能得到什么、什么问题得到修复，以及需要注意什么。同一体验涉及多处修改时合并成一条，重要变化靠前。

测试数量、测试命令、验收经过、内部重构、文件路径、接口字段、提交编号、构建编号、文件摘要和资产上传状态等用户无感知内容不写入。必要的工程与验收资料仍放在内部记录。技术变化确实影响使用时，改写为用户能理解的结果或操作要求；英文专业名词确需出现时附中文说明。

为兼容程序内纯文本显示，仅使用一级版本标题、三个二级标题和单层 `-`（列表符号）。条目内不使用加粗、行内代码、表格、图片、链接或其他排版语法，也不另加摘要、测试结果或已知问题章节；影响使用的限制归入“升级注意”。

复制以下结构，替换版本号和条目内容后使用：

```markdown
# Voice Terminal（语音终端）v版本号

## 新增与改进

- 写明新增能力或改善后的使用体验。

## 修复

- 写明出现问题的场景及修复后的结果。

## 升级注意

- 写明升级所需操作或影响使用的限制；确认无需额外操作时填写“无需额外操作。”。
```

## 每次更新的填写流程

1. 更新前确认上次实际交付和本次本地程序的完整差异，筛选用户可感知内容。
2. 在对应版本文档中按三个部分合并、去重、精简；先前已记录且仍属于本轮交付区间的内容保留。
3. 本机更新或分发交付前，核对条目与本轮实际程序一致；更新成功后，在内部交付记录中登记实际版本、构建和对照依据，供下次更新使用。
4. 推送 GitHub 发行资产前，再以上次对外更新核对完整区间，并将最终内容收敛到同一份版本文档；按既有发布流程提交、推送，再运行发行脚本。
5. 发行脚本将版本文档用于 GitHub 发行正文，并仅转换标题、列表符号后写入 `update.json`（更新清单）的 `releaseNotes`（中文发行说明）。程序内直接显示该字段；两端条目、分组、顺序一致，不另写或删减一份应用内日志。

发布前只需检查：对照区间完整、正文只有三个部分、条目对用户有意义、升级注意准确，以及两端共用同一份文档。发布后需要纠正日志时，修改该版本文档，并按既有发行流程同步正文、更新清单及配套摘要，不能只改一端。

本规范从后续更新开始执行；已经发布的历史日志不要求追改。现有目标版本文档在下一次更新或发行前按本规范整理。
