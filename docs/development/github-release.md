# GitHub（代码托管平台）源码与发行发布

公开仓库为 `wet86y/voice-terminal`，源码采用 Apache-2.0（开源许可证）。Windows（操作系统）发行资产使用本机运行资源打包，由维护者在本机构建。

## 发布前填写更新日志

遵循[更新日志填写规范](release-notes.md)，在 `docs/releases/v版本号.md`（对应版本更新文档）中只填写“新增与改进”“修复”“升级注意”。对照上一次实际对外更新与本次本地程序的完整变化，本机已更新但尚未公开的内容应一并合入；不能只汇总最近几次 Git（版本控制）提交。

GitHub 发行正文与程序内日志共用该文档，不能另写一份。发行脚本只转换标题及列表符号，再写入 `update.json`（更新清单）的 `releaseNotes`（中文发行说明），因此条目使用简单文本列表。测试、构建和交付证据保留在内部记录，不混入用户日志。

## 发布发行版

1. 核对更新日志与本轮实际程序一致，将目标源码与对应版本文档一并提交并推送到 `main`（源码主分支）。
2. 登录 GitHub CLI（GitHub 命令行工具），确保拥有发行权限。
3. 在 Windows 的仓库根目录运行 `npm run github:release`（只构建并发布发行版）；需要同时更新本机时运行 `npm run github:release:local`（同包更新本机并发布），不要先后运行本机完整发布和完整分发构建。入口与复用规则见[开发、构建与同包交付流程](desktop-pipeline.md)。
4. 成功后在内部交付记录登记实际交付版本、构建及本轮对照依据，作为后续更新的起点。

脚本按内容准备分发资产，再核对 `package.json`（项目清单）、产品与安装器构建戳、`package-info.json`（程序包信息）、`delivery.json`（交付记录）、安装器大小和 SHA-256（完整文件摘要），生成带中文字段说明的更新清单和资产摘要列表。不一致时在上传前停止。产品包与安装器均可在输入和产物摘要匹配时复用；已有包安装不重组包。

首个发行版为 `v0.9.0`。后续版本使用根项目清单的版本号与对应的 `v<version>`（发行标签）。脚本拒绝未提交的工作区，或尚未与 `origin/main`（远程源码主分支）同步的本地 `main`。

## 发行资产

- `VoiceTerminalSetup.exe`（自包含分发安装器）。
- `delivery.json`（已核验的程序包与安装器交付记录）。
- `update.json`（包含同一份中文更新日志的应用更新清单）。
- `SHA256SUMS.txt`（安装器及两份记录的完整文件摘要列表）。

程序读取最新公开发行的更新清单。用户主动开始更新后才下载安装器，核对准确字节数与完整摘要，再交给当前工作区的安装事务。

## 旧版在线更新兼容验收

分发器必须接受已下发程序的 `nonce`（单次编号）格式：十六进制纳秒时间戳、一个连字符和十六进制 `PID`（进程编号）。0.9.0 在启动分发器后正常退出；分发器应在进程存活时核对创建时间和路径，明确已退出时继续检查工作区空闲状态并取得独占锁。查询权限不足不能当作进程已退出。

修订分发器后，使用 `scripts/check-app-update-handoff.py`（应用更新交接验收脚本），传入 `--previous-package`（旧版正式程序包）及 `--previous-sha256`（公开交付记录中的程序包摘要）。脚本使用新的隔离工作区，分别通过正式 `--app-update-config`（应用更新配置入口）验证仍在运行和已退出的旧程序，核对一次性配置消费、目标版本、固定文件摘要、工作区身份及数据保留。成功后回收测试工作区，仅保留报告；不使用真实用户数据。

已下发的旧程序无需修改。在线发行修订时必须同步替换 `VoiceTerminalSetup.exe`（分发器）、`delivery.json`（交付记录）、`update.json`（更新清单）和 `SHA256SUMS.txt`（文件摘要列表），让旧程序下载到的安装器大小和摘要与清单一致。仅替换安装器会使旧程序在下载校验阶段拒绝更新。

## 同版本撤回与重新发行

需要撤回缺陷发行版并保留版本号时，按以下流程执行：

1. 保存原发行记录，再撤回指定版本的公开发行，检查公开最新入口已不再指向该缺陷发行版。
2. 将修复提交并推送到 `main`（源码主分支），保持构建工作区干净；核对目标标签实际指向的提交。`--target main`（创建标签时的目标分支参数）不会自动移动已经存在的标签，同版本重新发行必须将标签绑定到已核对的修订提交。
3. 从该源码重新运行 `scripts/distribute-desktop.ps1`（完整分发构建脚本）。等待正式程序、程序包、安装器和交付记录全部生成；构建过程中目录可能暂时包含不同批次的产物，不能直接发布。
4. 用本轮普通安装器执行真实旧版交接验收，再运行 `scripts/publish-github-release.ps1 -SkipBuild`（复用已构建并验收的资产发布）。该参数不跳过程序包摘要、构建戳、交付记录及安装器大小和摘要校验。
5. 发行脚本自动回下载四项资产，逐项与本机资产比较完整摘要，同时核对发行正文、最新入口及标签提交，记录 `.local/cache/reports/release-public-latest.json`（公开核验报告）。失败时单独执行 `scripts/verify-github-release.ps1 -Tag v版本号`（重试公开核验），不重新编译或安装；进行发行后纯文档补录前完成核验。

源码、发行标签和本轮资产应保持可追溯关系。发行后的纯文档补录可以另行提交，已验证的发行标签继续指向实际用于构建的提交。本次 0.9.1 的执行结果见[重新发行验收](../testing/app-update-handoff-20261018.md#线上重建与重新发行验收)。
