## 回放和报告

`voice_terminal.analysis.replay` 的 V0.3 报告保存配置摘要、事件计数、请求并发、Wait/Speak/工具/输出摘要、延迟、脱敏错误和结果状态。默认不保存完整 LLM messages、工具正文、密钥或原始音频；`--expect expectations.json` 可声明允许无 PCM、最小历史、请求上限、并发上限和最小 Speak 次数。合法等待、预期阻止/中断、内部失败和 settlement/ASR 超时分别计数，截止时仍有 Agent/输出 Task 会失败。

示例：

```powershell
python -m voice_terminal.analysis.replay logs\evaluation\audio\query-first12.wav `
  --config config\v0.3.yaml --expect logs\evaluation\v03-expect.json `
  --output logs\evaluation\v03-replay.json
```

`logs/` 属于本地运行目录并被忽略，报告不得提交仓库。

本轮真实服务样本（均为合成文本、内存播放器）：ASR/Analysis/Voice Server health 均 READY。三组 v0.2/v0.3 对比中，v0.2 三组均在模型结束前出现首 TTS/首 PCM；v0.3 两组完成同样的重叠证据，另一组模型选择 `wait_for_input`，因此是 `no_speech` 失败样本，不能声称三组全部通过。三次“等待、等待、回答”语义复验中两次得到 0/0/1 Speak，一次第三段仍等待；这是模型决策波动，保留为未完成的稳定性证据，不修改断言来掩盖它。此前的 MiniMax cancel 后同连接复用样本只证明过一次成功，不能推导为可靠契约；2026-09-07 的生产日志已发现 flush/cancel 后复用连接可产生零 PCM，当前实现改为关闭该连接。内存 fake 播放竞态仍有自动化覆盖。

## 2026-09-07：Bidi 输出诊断和连接隔离

本次诊断针对“LLM 已返回语音文本但没有播放”以及“播放数秒后停止”。审阅生产 `voice-server.log` 后，关联的 DeepSeek 请求均为 HTTP 200，未发现 MiniMax `task_failed`、429、rate-limit 或配额错误；因此没有证据把该现象归因于 LLM 调用失败或 TTS 限流。

日志中有一次受保护真人插话：播放约 25.9 秒后，近端语音持续约 279 ms，随后出现 `task_canceled`；该次取消符合既有插话门控。原日志还发现独立的确定性故障：同一 Bidi 连接在收到 `task_flushed` 或 `task_canceled` 后被复用，下一次 `task_continue`/`task_flush` 获得 provider 完成确认却返回零 PCM；播放器的 `enqueued=0`、`played=0` 表明音频从未进入播放队列，旧代码却可能把它结算为 completed。

修复将 `task_flushed` 和 `task_canceled` 都标记为连接不可复用；输出清理关闭该会话，下一次 Speak 建立新连接。TTS 管线记录已发送文本和累计 PCM。已发送文本且零 PCM 时记录 `controller.tts_empty_audio` 与 `TTS_EMPTY_AUDIO`，仅在完全未传达时以新会话重试一次；再次零 PCM 则记录 `TTS_EMPTY_AUDIO_RETRY_FAILED` 并以 `failed` 结算。`episode.speech_invalidated`、`episode.speech_final` 和 `agent.trace` 记录固定输出身份、终止原因、播放快照与脱敏插话证据，方便以后区分真人插话、噪声候选、陈旧事件和 provider 音频失败。

真实 MiniMax Bidi 短文本 smoke（内存播放器、无物理设备）验证 provider 接受 `voice_setting.emotion`：`calm` 收到 141,732 bytes PCM（connection 1），随后 `happy` 收到 153,066 bytes PCM（connection 2）；两次 flush 后均为不可复用，第二次确为新连接。该结果验证字段接受、PCM 返回和连接隔离，不证明扬声器、耳机或自然语音表现。
