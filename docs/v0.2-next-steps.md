# v0.2 后续实施交接：补齐实时预测证据与发布验收

本文件是 v0.2 当前实现之后的执行计划。它把“代码已经接入”和“能力已经验收”分开，供下一次开发会话直接接手。本次已按阶段 1、2、3 执行并在阶段 3 结束后暂停；阶段 4、5 等待后续安排。

## 0. 执行约束

- 保留工作区现有改动。开始时先检查 `git status`、差异和项目指令；禁止重置、清理或覆盖不属于本次工作的内容。
- 不读取或输出密钥内容，继续使用现有配置加载机制。
- 新能力继续默认关闭，以 `config/v0.2.yaml` 显式启用；本计划不自动修改默认配置，不自动提交 Git，不发布。
- 先完成阶段 1、2、3，形成可审阅结果后停止。不要因为测试通过就自动进入真人设备验收。
- 下载慢时，只对下载进程临时关闭代理；不修改全局代理。只要下载仍有进展就等待，不重复下载已校验的模型。
- 每个阶段都更新验证记录，分别注明“代码已实现”“确定性测试通过”“真实服务验证通过”和“真实设备验收通过”。

## 3. 阶段 2：并发边界、身份校验与诊断时间线

### 3.1 复现过期预测启动工具的窗口

重点检查 `RealtimeController._predict` 与 `SpeculativeTools.select`。预测返回后的工具选择包含异步参数规范化和缓存新鲜度检查，输入可能在等待期间改变。先写可控门闩测试，再根据失败结果修改实现。

必须覆盖：

| 暂停点 | 变化 | 期望 |
|---|---|---|
| 参数规范化期间 | `input_revision` 增加 | 不创建过期预测工具任务 |
| 缓存新鲜度检查期间 | generation 改变 | 不发布旧 generation 工具状态 |
| 选择等待期间 | 输入封口 | 不再启动预测预取，最终调用仍可执行 |
| 选择等待期间 | 停止监听或开启新轮 | 不创建旧轮任务，不污染新轮 |
| 第一个工具处理后 | 当前输入改变 | 同一预测返回的后续工具不继续启动 |

实现约束：所有必要异步准备完成后、创建任务前，检查 turn、generation、revision 以及仍处于收听阶段；最后一次检查到任务创建之间不得再有异步等待。工具事件也要携带并校验适用身份。最终模型使用最终 generation 的规则，不能被预测阶段的“仍在收听”限制误伤。已启动的只读任务可按既有有界策略完成，但过期结果不能改变当前决策。取消和过期属于正常控制流程，不应升级为语音服务故障。

### 3.2 增加可解释的时间线

记录以下时间点和结果：

- 预测快照生成、请求发出、返回、采用或丢弃；丢弃原因包括 revision/generation 过期、轮次结束、输入封口、超时和无效返回。
- 工具选中、实际执行开始、执行结束、最终模型选中、复用与否；区分排队时间和线程实际执行时间。
- 最终输入封口、最终请求发出、首正文 token、首段 TTS、实际播放开始。

全部时差使用后端单调时钟计算，事件带适用的 turn、revision、generation。`first_prediction_ms` 保持“首个被采用的预测结果”的含义；首次请求发出另设字段。未发生的值为 `null`。诊断数据保持有界，继续复用事件和现有报告机制。工具节省时间只报告时间线上实际可计算的等待重叠量，不估算未执行的对照路径。

同步更新 `docs/websocket-protocol.md`，保证旧前端忽略新字段和新事件仍能展示主链。

- 过期预测不能创建预取或更新当前工具状态。
- 最终请求不等待预测连接结束。
- 报告能区分“未发出、返回过晚、被回改淘汰、超时、无效返回、工具失败”。
- 相关 Python 测试通过；若协议或前端有改动，补跑前端检查。

## 4. 阶段 3：验证持续讲话期间的多次预测与预取收益

这是本批工作的核心交付，完成后暂停。

### 4.1 固定可重复输入

先按真实采样速度使用可重复录音或本地合成语音，合成语音只用于工程链路验证，不作为真人端点准确率证据。至少准备：

1. 15–25 秒持续表达，逐步增加信息，验证同轮多次预测。
2. 前半段明确要求查询项目文档、后半段继续补充条件，给文件预取留下时间。
3. 先说一个查询条件，再自我纠正为另一个条件，验证旧意图失效。
4. 预测请求仍在等待时结束输入，验证最终请求独立发出。
5. 800 ms 停顿后继续讲话，验证续说回归。

文件搜索只匹配文件名；查询必须使用许可目录 `docs` 中实际存在的文件名关键词，避免把工具语义不匹配误判成预取失败。

### 4.2 确定性测试

- 以受控预测延迟验证单在途、只保留最新待处理快照。
- 覆盖重复 partial、快速增长和回改，确认不形成请求积压。
- 至少两个不同 revision 在各自有效期间被采用。
- 覆盖工具运行中、完成、失败、文件改变后的复用和重新读取。
- 使用不少于 100 次模拟结束尝试计算 `commit_to_final_llm_ms` p95，目标仍为不超过 50 ms，不包含云端响应。

### 4.3 真实模型回放

使用现有 Smart Turn、SenseVoice、Paraformer、DeepSeek 和 MiniMax，对持续表达与提前查询各做 3 次固定输入回放，保存逐次事件、报告和输入摘要。验收要求：

- 至少一个持续表达用例在结束前采用两个或更多有效预测。
- 至少一个查询用例在结束前启动文件工具，最终模型重新选中相同调用并按文件版本正确复用。
- 没有旧 revision/generation 结果影响当前意图，无重复用户消息。
- 预测输出、工具参数和工具 JSON 不进入 TTS。
- 最终回答只提交一次完整历史交换。

若未达标，先用时间线区分 ASR 更新不足、稳定分段太晚、云端响应过慢、结果持续过期和工具请求无效，只修复已定位环节并复测相关用例。不能用独立工具测试替代整条实时回放证据。

### 4.4 阶段交付与暂停点

更新 `docs/v0.2-validation.md`，记录修改、测试命令和结果、输入与报告位置、多次预测是否成立、预取是否发生在结束前、最终是否复用、最终调度 p95 及剩余问题。关闭本次启动的测试进程，然后暂停；不自动开始真人设备测试或默认启用。

## 5. 阶段 4：后续安排后再做的 Worker 与长音频验收

本阶段不在本批自动执行。

### 实际 Worker 链路

- 从实际配置解析 ASR Worker 地址，使用应用层 health 响应确认模型就绪，移除启动脚本对固定 `127.0.0.1:8766` 的依赖。
- 增加真实 ASR Worker WebSocket 回放路径，同时保留进程内模式作为快速诊断路径。
- 覆盖 ASR 断线、Analysis Worker 不可用、停止监听和重新开始；错误原因可见，旧文本、工具和 PCM 不泄漏，资源有界。

### 长音频

复测接近 30 秒、45 秒、接近 60 秒和超过 60 秒的输入。每段不超过 30 秒，结果按音频顺序拼接；标签保留分段范围，不强制压成单一情绪；失败、超时或缺段整轮回退 Paraformer；超过上限标记 `max_duration` 并让后续讲话进入新轮；轮次结束释放音频和任务引用。

## 6. 阶段 5：后续安排后再做的自然语音、设备和发布判断

使用至少 20 条有人工核对文字的自然语音，固定环境分别运行 v0.1/v0.2，记录字符错误率、误结束次数、结束至首音 p50/p95、精修回退率、各进程 CPU/内存峰值、预测采用/丢弃原因和预取复用情况。耳机和扬声器分别验证结束前续说、精修/LLM/TTS 排队期间续说、实际播放后中断、连续多轮和停止恢复。内存播放器时间不能标作真实设备播放时间。

只有在旧轮数据不泄漏、核心多次预测和预取有真实服务证据、长音频和异常降级通过、自然语音与设备对比没有未解决退步时，才评估是否默认启用。默认启用不属于本计划自动动作。
