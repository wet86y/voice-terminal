# Voice Terminal 产品化基线 · P0.1

> **状态：** 已确认的产品体验基线。P0.1 是产品体验里程碑，不是 npm 包或正式应用版本。

## 版本体系

Voice Terminal 从 P0.1 起采用双轨版本，避免产品界面原型影响稳定语音运行时的发布语义。

| 版本线 | 标识 | 含义 |
| --- | --- | --- |
| 稳定运行时 | `V0.7.x` | 当前 Python Voice Server、ASR、LLM、TTS、KWS、WebSocket 协议与研发控制台；仅接受稳定性修复和兼容性维护。 |
| 产品体验里程碑 | `P0.x` | 产品化设计、独立 UI Demo、统一应用接口和桌面封装的开发里程碑；不是正式应用版本。 |
| 下一正式产品版本 | `V0.8.0` | 新产品 UI 已接入真实运行时、设置 API 可用，并成为默认 Web 用户入口。 |
| 桌面应用预览 | `V0.9.0` | Tauri 2 托管 Python Voice Server sidecar 的可安装 Windows 预览版。 |
| 稳定产品版本 | `V1.0.0` | 可分发 Windows 产品：安装、更新、日志、设置、会话恢复与基础稳定性验收完成。 |

首个视觉前端的名称为 **Voice Terminal · UX Prototype P0.1**。根目录和 `apps/web` 的包版本继续保持 `0.7.0`，P0.1 不修改发布版本号。

```text
V0.7.x Runtime → P0.1 / P0.2 / P0.3 → V0.8.0 → V0.9.0 → V1.0.0
```

## 产品定位与边界

Voice Terminal 是全天候 Windows 桌面语音助手。最终由 Tauri 2 管理应用窗口、应用生命周期和 Python Voice Server；用户不应需要了解 Python、端口或 WebSocket。

P0.1 不改变 V0.7 的语音链路、会话账本、WebSocket 协议或研发控制台。它建立产品界面基线和完全隔离的视觉 Demo。当前研发控制台仍保留为开发与诊断入口，不作为最终产品首页。

产品用户界面只有两个一级页面：**首页**和**设置**。

## 首页：三列专业工作台

首页按“左 Shadow、中语音助手、右实时会话”的三列布局组织。中列是状态与响应球的视觉焦点；右列保留完整会话阅读面积，左列以紧凑监督摘要为主。

三列在宽屏下使用协调的“左、中、右”比例，避免系统卡或 Shadow 卡被压缩成侧栏。上下文占用与缓存命中统一放在各信息面板的底部：中列只保留即时语音状态、延迟和模式；Shadow 底部额外提供 `low / high / max` 思考强度的产品控制位。

### 中列：系统控制与响应球

- 启动或关闭语音助手运行状态；应用本身仍可继续驻留。
- 展示待机、等待唤醒、聆听、理解、播报、异常等用户可理解状态。
- 使用美观的语音球提供状态反馈：待机低频呼吸、聆听输入脉动、思考非录音缓动、播报输出脉动。
- 展示产品级感知延迟指标“用户说完 → AI 开口”。该指标由前端使用本地单调时钟测量：收到本轮 `session.state` 的 `FINALIZING` 时开始计时；如果服务端没有发送这个状态，则以对应的 `input.finalized` 作为兼容回退；收到对应轮次的 `speech.started`（播放器首次实际消费该事务的 PCM）时立即停止。计时不读取 `metrics.snapshot`，也不等待 `speech.completed`，因此后端延迟快照不会覆盖正在展示的实时值。
- 响应延迟的展示单位固定为：小于 `1000 ms` 时显示整数毫秒（例如 `813 ms`）；大于或等于 `1000 ms` 时显示秒，最多保留两位小数（例如 `1 s`、`1.23 s`）。
- 提供快速、均衡、深度三种运行模式。

P0.1 语音球只使用模拟脉动。P0.2 需要由后端提供归一化的本机输入/输出音频电平事件，产品页面不得自行采集或推断音频。

### 右列：实时会话

- 显示用户 ASR 草稿与最终文本，视觉上明确区分“实时识别”和“已确认”。
- 显示主 LLM 的正式 `speak` 队列、播报中内容和已结算内容。
- 未完整传达、被打断或被替换的回复必须弱化呈现，不能表现为用户已经完整听到。
- 深度模式附加展示后端明确提供的可读 reasoning 摘要。

产品页面只展示面向用户的推理摘要；不得展示模型私有原始推理链、内部 schema、请求 ID、token、追踪栈或调度细节。

实时会话标题下投影 `context_token_estimate`、`context_limit_tokens`、`context_usage_percent`、`provider_cached_tokens`、`provider_input_tokens` 与 `provider_cache_hit_ratio`。provider 尚未返回 usage 时显示“等待首个模型响应”，不得伪造零命中。

### Shadow Agent 运行时区

- 默认常驻，支持折叠/展开。
- 展示当前状态、任务目标、运行步骤、工具状态和近期观察。
- 不提供输入框；用户继续通过正常语音会话补充、修正或撤销意图。
- 接入 Shadow 的实时总结模型输出，作为可读的“当前工作简报”。
- 状态卡下以相同规格展示 Shadow 自身的上下文占用和缓存命中指标；只投影聚合 usage，绝不展示 prompt、完整 trace 或内部 token 调度细节。

V0.7 已有 session 级单一 Shadow Runtime 和状态观察机制；P0.2 需要将它稳定投影为产品可用的摘要和状态数据，而不是直接暴露研发 trace。

## 设置：首发标签

| 标签 | 首发内容 | 生效方式 |
| --- | --- | --- |
| KWS 唤醒词 | 启用状态、中文/英文唤醒词、灵敏度 | 启用即持续待机；不提供独立待机或生效时长开关；由 P0.2 设置 API 定义热更新或受控重启语义。 |
| 主 LLM 人格 | `instructions.md`、`personality.md`、`user.md` | 保存后在下一次新会话读取。 |
| Shadow Agent 指令 | `config/shadow_agent/instructions.md` | 保存后在下一次新会话读取。 |
| 静默等待事件 | 默认 30 秒的最终静默检查/回待机时间 | 保存后在下一次新会话使用。 |
| 模型管理 | 供应商连接、能力隔离模型池、TTS 配置和运行时分配 | 验证后入池；确认后中止当前会话并重启受影响服务。 |

30 秒“静默等待事件”不是用户一句话结束的判定。当前约 1.4 秒的 Smart Turn `hard_silence_ms` 仍负责语句结束；30 秒负责 KWS 唤醒或会话后长期没有有效用户事件时的最终静默检查与回待机。

前端不得直接修改 YAML、`.env.local` 或 Python 内部对象。凭据等受保护字段不应向前端回传明文；未来设置 API 只能返回已配置、未配置、验证失败等非敏感状态，并提供受控的写入、验证或删除操作。

## 模型管理基线（P0.1 交互、P0.2 实现）

模型管理按四层组织，不能把供应商连接、模型条目和运行时选择混为一层：

```text
受管目录扫描 / 有效配置导入 → 供应商连接配置 → 按能力分离的模型池 → 运行时分配
```

### 供应商、模型池和凭据

- `ProviderProfile` 保存连接名称、来源、协议、服务地址、能力域、发现能力、`credential_ref`、最近验证结果和时间；**不保存 API Key**。
- `ModelEntry` 具有稳定 ID、显示名、原始模型 ID、所属供应商、能力类型、来源、验证/健康/隐藏状态，以及本地路径和指纹（如适用）。能力至少区分 `llm`、`tts`、`local_kws`、`local_asr`、`local_vad`、`local_analysis_endpoint`、`local_analysis_refine`。
- 文字 LLM、TTS 和本地模型是独立池。同一供应商的文字模型与 TTS 模型使用不同能力条目，不能交叉分配。
- `TtsProfile` 引用一个已验证 TTS 模型，单独保存 `voice_id`、情绪模式和默认情绪、格式、采样率、传输方式、调度方式与字幕配置；验证按“模型 + 音色 + 传输配置”执行最小合成探测。
- `RuntimeAssignments` 包含 `voice_llm_model_id`、`shadow_llm_model_id`、`status_llm_model_id` 与 `tts_profile_id`。三个 LLM 角色各自保存 `reasoning_effort` 与 `max_context_tokens`，不修改共享 `ModelEntry`；状态汇报角色固定 `reasoning_effort = none`。本地模型不写入 P0.2 运行时分配。

Voice Server 是凭据 owner。Windows 首发使用 Windows Credential Manager 的 Generic Credential；实际 API Key 只通过受控 `CredentialVault` 写入系统凭据库，配置和模型池仅保存 `credential_ref`、状态和元数据。服务启动时必须确认选中的 `keyring` backend 是 Windows Credential Manager。若不可用，产品 UI 保存 API Key 的功能必须禁用并给出可诊断错误，**不得**退回 YAML、JSON、浏览器存储或弱保护文件。

API 响应、日志、异常、审计记录、WebSocket 事件和诊断导出均不得包含 API Key。现有 `.env.local` 或进程环境只用于导入“凭据是否存在”的状态；产品不会读取、迁移、展示或回传其明文。

### 发现、验证、导入和移除语义

- OpenAI 兼容服务优先尝试其模型列表接口；发现到列表后由用户选择需要入池的模型，避免为长列表中的每个模型自动产生探测费用。服务不支持发现时，用户可输入自定义模型 ID。两种路径都必须先完成真实最小能力测试，才可进入模型池；LLM 测试端点、凭据、模型 ID、流式/结构化响应所需能力，TTS 测试最小合成并立即丢弃返回音频。验证可能产生极少量提供商费用。
- 暂存验证请求中的 API Key 只存在于该请求生命周期。验证失败时，不写入凭据库、不创建供应商，也不创建模型池条目。验证成功后的提交必须原子完成：写入 Credential Manager、写入无密钥 `ProviderProfile`、写入成功模型条目，再返回脱敏快照。
- 扫描只读取当前 `model_dir`、模型 manifest 与项目定义的受管子目录；绝不扫描任意磁盘路径。扫描会记录路径、类型、完整性、文件指纹与健康状态；扫描发现的新条目可自动加入对应本地池。
- 现有有效配置导入读取合并后的 default/local YAML：导入主 LLM、Shadow provider 的继承关系、TTS provider 和模型；条目明确标为“来自现有运行时配置”。用户可创建产品托管连接替代它。
- “删除模型”只表示从产品模型池和分配中隐藏，不删除任何本地模型文件，也不移除现有 YAML/.env 配置。已隐藏条目有恢复入口，并且后续手动或定时扫描不得将它悄悄恢复。
- 已分配的条目必须先改用其他可用条目或解除分配，才能隐藏。隐藏、不可用或验证失败的条目不能被分配。

### 立即应用与能力边界

用户保存模型分配前，服务必须校验语音 LLM、Shadow Agent 与状态汇报模型都只选择已验证的 `llm` 条目，TTS 只选择已验证的 `TtsProfile`。状态观察器是独立 provider：只使用已经提交的 Shadow trace 的受限前缀、按角色上下文上限裁切、始终禁用工具和思考，并遵守受控的最大输出长度。界面先展示受影响组件和“会中止当前会话/播报”的确认信息；确认后：停止当前语音会话和活动 TTS、重建受影响的主 LLM / Shadow /状态汇报 provider / TTS 组件、发布受控重启状态和结果。若重启失败，必须保留上一份已验证有效的分配并返回可读错误。

P0.2 不开放 KWS、ASR、VAD、Smart Turn、SenseVoice 的任意运行时替换。它们仅参与受管目录扫描、展示、隐藏和恢复；这避免“模型管理”在产品早期绕过 V0.7 的完整启动与健康检查链路。

## P0.1 UI Demo

`/ui-demo.html` 是独立的 Vite 多页面入口，名称为“Voice Terminal · UX Prototype P0.1”。它只使用固定模拟数据和内存状态：不创建 WebSocket、不申请麦克风权限、不读取或写入真实设置、不连接或控制 Voice Server。模型管理页同样离线：其扫描、连接验证、API Key 输入、模型入池、隐藏/恢复和重启都是视觉模拟，刷新页面即恢复默认值。

P0.1 的模型设置采用固定三段结构：首先是 API 供应商连接与密钥验证；随后是三张系统模型配置卡（语音交互主模型、Shadow Agent、状态汇报模型），该层只展示当前分配并设置各自的上下文上限；最后是默认折叠的模型池。模型池标题显示 LLM、TTS、本地与隐藏计数，展开后才渲染已有模型列表。每个条目以“供应商 + 显示名 + 原始模型 ID”区分，避免跨厂商同名模型混淆；用户可删除产品托管的 API 模型，或隐藏/恢复只读本地模型，任何本地文件均不会被删除。

P0.1 用于确认三列工作台、对话信息层级、Shadow 展示和设置页信息架构。视觉与交互稳定后，P0.2 将以替换模拟适配器的方式接入真实数据，而不是推倒重建产品组件。

## Product UI 当前实现与切换性能

当前迁移中的真实 Product UI 由根入口 `/` 提供，使用 `ProductApp.vue` 和
`useProductAdapter.ts` 接入 Product API、Voice Server WebSocket 与设置 API。它与上面的
`/ui-demo.html` 是两个明确隔离的入口：前者用于真实运行时和开发回放，后者继续作为不连接
后端的视觉原型。

开发回放入口为：

```text
/?replay=voice-shadow
```

它从本地旧日志提取一组 Shadow Agent 与语音交互的公开产品投影，便于检查长会话、Shadow
时间线、上下文/缓存指标和左右消息布局。回放只读，不把日志中的 prompt、工具参数、原始
provider 数据或凭据带入页面；它不是生产数据源，也不会改变后端状态。

### 当前会话播报与设置反馈

Product UI 的“当前 Voice Terminal 会话”按单个 `conversation_id + speech_id` 展示播报轨迹。
等待或正在播放的事务属于临时播放队列；收到物理播放结束事件后，前端将已知文本转入当前会话历史，
并保留该事务的完成、失败、打断或替换状态。后到的 `speech.completed` 只更新同一条轨迹的最终结算
字段，不会让已播放内容重新消失，也不会把多个 TTS 事务合并成一条模糊的当前队列。切换 Episode、
重置会话或断开连接时清理这份会话级本地投影，重新连接后以服务端快照恢复。

设置页的成功反馈和只读操作提示在出现后保持 5 秒，随后经过约 420 ms 的淡出过渡并从 DOM 移除；
连续操作会重新开始计时，错误提示仍保留显式关闭入口。该行为属于前端反馈生命周期，不改变设置 API
的保存、生效或错误语义。

Product 页的导航性能契约如下：

- 工作台和设置页保留组件实例，用 `v-show` 隐藏未激活页面，避免导航时重复挂载大型设置表单；
- 桌面端两个页面使用固定视口层，页面整体高度保持在浏览器视口内，长内容只在对应面板内滚动；
- Product 大面板使用实体渐变背景，不使用大面积 `backdrop-filter`；
- 运行态语音球、halo、Shadow 状态点和播报点使用静态状态表达，不使用持续的 transform 或
  box-shadow 动画，避免外部 Edge 在切换时重复合成大型图层；
- 导航的唯一状态变更仍是普通 `click` 更新页面 ref，不通过 `pointerdown` 另建一套兜底流程，
  也不在点击时发请求或等待后端；
- 以上规则只作用于 `.product-shell`，不改变旧版 UX Prototype 的视觉动画。

切换验收至少覆盖外部 Edge 中 `工作台 → 设置 → 工作台` 的连续往返，并检查设置页和工作台
均可再次进入；若出现卡顿，优先记录浏览器 Performance/GPU Trace，不要先添加第二套导航事件。
