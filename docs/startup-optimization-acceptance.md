# 启动优化实施与验收

本文件记录首轮识别优化。[第二轮并行启动验收](startup-parallel-acceptance.md)包含代理提前启动、95% 物理内存阈值与三路重型模型加载的最终规则。

日期：2026 年 10 月 7 日。首轮实施范围是 ASR（语音识别）按需导入，以及识别与分析进程按资源预算并行加载。本文件中的两路调度、语音服务延后启动和正式构建标识均为首轮交付状态；第二轮已提前开放语音服务轻量接口、并行启动 DSH（代理执行宿主），并将重型模型加载上限改为三路。DSH（代理执行宿主）的内部加载实现继续沿用原版本。

## 实施行为

识别加载器仅对 FunASR（语音框架）1.4.14、已校验的两个入口文件摘要及当前流式模型配置启用按需导入。适配使用临时内存加载器，不改写已安装运行库、模型配置或权重。保留官方模型构造、流式推理、累计转写、空最终包刷新、独立缓存预热和显卡失败后的处理器回退。

注册范围包括流式识别模型、编码器、解码器、预测器、音频前端、分词器和模型构造需要的频谱增强。框架存在同名解码器重复注册，已通过完整加载对照确认实际选择 `funasr.models.e_paraformer.decoder`（原加载路径最终注册的解码器），按需路径采用相同来源。可选声纹聚类依赖延后至实际选择声纹子模型的分支，其他模型家族不提前扫描。

以下情况沿用完整导入：未知配置、额外模型或外部代码、运行库版本或入口摘要改变、已经导入框架、明确选择完整导入。按需导入失败时清理本次框架模块、撤销临时查找器并恢复完整导入。

监督器在环境检查后优先放行识别加载，按当前资源决定是否再放行分析加载。条件包含可用物理内存、剩余系统提交内存、处理器使用率及线程预算；两项都可能使用显卡时还检查空闲显存。采样不加载推理框架，也不创建显卡计算上下文。

初始保守预算如下，属于放行估计，并非宣称的实际占用：

| 组件 | 常驻内存预算 | 私有提交预算 | 显存预算 |
| --- | ---: | ---: | ---: |
| 语音识别 | 3 GiB | 7 GiB | 2 GiB |
| 语音分析 | 4 GiB | 10 GiB | 3 GiB |

GiB（以 1024 为基数的容量单位）。额外保留 1 GiB 物理内存、2 GiB 提交内存及 0.5 GiB 显存。已经分配的物理与私有提交从加载余量中扣除；显存完整预留至加载完成。初始化最多两路，采样缺失或预算不足时采用串行。

排队组件显示“等待资源”，仅在真正创建进程后开始计算工作进程启动超时。识别或分析失败不取消另一项加载；两项完成检查后再启动语音服务，随后检查受委托组件，最后更新 `startup_complete`（完整启动标识）。退出会取消未放行任务和加载等待，已创建进程仍由原进程组回收。环境恢复重试也复用同一模型调度。

`native_threads`（各进程原生线程预算）明确设置识别线程数时，通过 `VOICE_MODEL_THREADS`（模型线程预算）传入模型加载器的 `ncpu`（张量计算线程数），避免加载器自行改回默认值。未指定时保留原模型的四线程默认值。

## 真实模型对照

使用正式程序随附的 Python（后端运行时）、同一流式识别模型和固定录音。六次测试均为独立新进程，使用相同的四线程预算，不清理操作系统文件缓存；准备时间包括导入、设备选择、真实模型加载和真实预热。它们是识别组件的诊断，不是整套桌面应用的启动基准。

| 测试 | 准备耗时 | 导入模块数 |
| --- | ---: | ---: |
| 显卡完整加载，首个样本 | 74.54 秒 | 399 |
| 显卡完整加载，后续样本 | 21.95 秒 | 399 |
| 显卡按需加载，复测一 | 8.57 秒 | 78 |
| 显卡按需加载，复测二 | 8.34 秒 | 78 |
| 处理器完整加载 | 19.54 秒 | 399 |
| 处理器按需加载 | 6.46 秒 | 78 |

首个完整加载样本受环境及缓存影响明显，不据此计算通用提速比例。后续样本仍显示导入开销下降；完整桌面应用耗时还包含语音服务及代理宿主，本轮不据此推断其最终启动时间。

六份结果已自动核对：录音摘要相同、最终文本相同、七次累计部分转写相同、空最终包处理正常、模型加载与预热通过、请求设备与实际设备相同。包含组件来源信息的记录也逐项一致；按需路径未导入 Transformers（文本模型库）或 scikit-learn（聚类依赖库）。

原始报告和汇总位于 `.runtime/startup-analysis`（本机启动诊断目录），六份最终记录为 `asr-full-cuda-1.json`（首个显卡完整加载）、`asr-full-cuda-2.json`（后续显卡完整加载）、`asr-selective-cuda-verified-1.json` 与 `asr-selective-cuda-verified-2.json`（显卡按需复测）、`asr-full-cpu.json`（处理器完整加载）、`asr-selective-cpu-verified.json`（处理器按需加载）。汇总是 `asr-comparison.json`（识别一致性对照）。

## 回归与调度验收

后端相关回归与桌面分发检查共 139 项通过，覆盖识别协议、流式累计文本、取消屏障、真实预热失败后的设备回退、资源策略、应用健康状态、恢复操作及受管进程回收。解码器来源校正后，加载器与调度相关 22 项检查再次通过。

新增行为检查包含：资源充分时两路加载、低内存时排队、线程预算或显存不足时串行、未知采样时串行、加载期间资源释放后动态放行、单分支失败隔离、语音服务等待两项模型、受委托组件结束前不标记完整启动、退出时不创建排队进程。

真实工作进程使用独立数据目录及空闲回环端口验收：环境检查约 4.2 秒完成，识别接口约 15.5 秒确认就绪，两项模型健康检查在约 40.6 秒全部通过。本机当时可用内存不足，分析进程在识别就绪前显示“等待资源”，实际采用串行。该样本没有创建语音服务或代理宿主，两项工作进程在结束后统一回收。原始状态过程保存在 `model-dispatch.json`（真实模型调度报告）。

本轮未重新进行原生桌面窗口的视觉验收，也没有测量完整桌面应用的新启动耗时。

## 本机正式程序更新

首轮发布时，正式程序切换到 `apps/desktop-20261007-asr-startup`（首轮应用构建）。该目录现保留供回退；当前启用的是 `apps/desktop-20261007-parallel-startup`（第二轮应用构建）。入口继续是 `.runtime/delivery/VoiceTerminal/VoiceTerminal.exe`（正式应用入口）。

以原正式程序 `apps/desktop-20261007-unified-startup`（统一加载页构建）为基底，仅覆盖七个后端文件，再使用原组装脚本的标准停机检查、清单校验、原子切换及失败回滚事务提交：识别加载器和工作引擎、资源策略、硬件内存查询、启动清单、进程监督器及启动资源预算。已核对新程序与原程序的实际文件差异恰为这七项，均与验收源码一致；其余程序文件保持原摘要，未将工作区中的其他未完成改动带入本次更新。

原入口二进制、Python（后端运行时）、模型、WebView2（网页运行组件）及 DSH（代理执行宿主）组件沿用原版本。保留旧应用目录以支持回退，不改变加载页、跳过入口或完整启动判定。

正式目录更新前后的 11,894 项数据文件及目录链接记录已核对：没有新增或删除，唯一变化是 `state/active.json`（当前启用程序记录）。设置、会话、凭据文件、日志和缓存保持原记录；扫描记录链接本身，不递归跟随外部目录链接。

启用组合清单校验和正式模块导入检查均通过。正式模块导入不会提前加载 PyTorch（张量框架）或 FunASR（语音框架）。发布记录是 `overlay-publish.json`（七文件更新与数据保留记录），模块核对是 `installed-module-verification.json`（正式程序实际差异与导入检查）。

## 对照与回退参数

`VOICE_ASR_IMPORT_MODE=full`（识别采用完整导入）用于复测原加载路径。`VOICE_STARTUP_PARALLEL=0`（重型模型加载采用串行）用于对照模型调度；在第二轮实现中，该参数不关闭轻量接口的提前监听，也不延后 DSH（代理执行宿主）的独立启动。参数属于进程环境，不写入用户设置。

`scripts/benchmark_asr_startup.py`（识别启动对照工具）提供 `--model-dir`（本地模型目录）、`--audio`（固定录音）、`--device`（请求设备，`cpu` 为处理器、`cuda` 为显卡）、`--import-mode`（导入方式，`full` 为完整、`selective` 为按需）、`--threads`（相同计算线程预算）及 `--output`（结果文件）。工具不访问麦克风或在线推理服务。
