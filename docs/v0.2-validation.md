## 阶段 4：真实 Worker 链路与长音频验收

### 代码已实现

- `AsrWorkerClient.health(timeout_s=2)` 发送带 `request_id` 的 health 请求，并等待匹配响应；超时、协议不匹配、非 READY、正常远端关闭和异常断线均有明确错误码。health 消息不会进入普通 ASR 回调。

### TTS 截断与时间限制排查

对 2026-09-05 的现场日志复核后，未发现回答因 v0.2 的 60 秒用户输入上限而被截断：出现问题的轮次从结束确认到 TTS 关闭只经过数秒，MiniMax 已返回 219 个 PCM 块（约 440 KB），而 LLM 仍继续产生最后一段文字。旧路径在 MiniMax 报告 `no close frame received or sent` 时直接抛出 `TURN_FAILED`，因此最后尚未发送的文字没有进入 TTS，且暂存回答为空。

当前实现把 TTS 失败降级为可见的 `tts.status=DEGRADED`，继续收集完整 LLM 文本并提交历史；健康 TTS 会等待不低于服务规定的 120 秒接收空闲窗口，回答和 PCM 播放排空不再使用固定 60 秒截止。TTS 已经失败时只给已排队音频短暂收尾时间，避免错误连接使轮次长时间悬挂。MiniMax 协议与速率限制说明见 [T2A WebSocket 文档](https://platform.minimaxi.com/docs/api-reference/speech-t2a-websocket) 和 [速率限制文档](https://platform.minimaxi.com/docs/guides/rate-limits)；密集手工测试期间还观察到 `rate limit exceeded(RPM)`，这属于服务限流，不能通过延长本地超时解决。

- 最新长文本现场轮次 `turn_20260905_191851_000009` 将原因进一步钉死在服务端限流：19:18:57 建立 T2A 任务，DeepSeek 共产生 291 个字符，应用向同一 TTS 任务发送 26 个 `task_continue`（日志累计 278 个待播字符），并在 19:18:59 发送 `task_finish`；19:19:08 MiniMax 返回 `task_failed`，错误为 `rate limit exceeded(RPM)`。随后接收循环共收到 451 个 PCM 块、899,826 bytes，按 32 kHz 单声道 16-bit 计算约 14.06 秒，之后不再有音频，因此听感表现为长文本中途停止。
- 该轮播放器缓冲峰值约 2,032 ms，未出现 `audio.player_overflow`、播放超时、`max_duration`、`ConnectionClosed` 或本地解码错误；19:19:12 仍正常发布 `turn.completed`。同一测试密集阶段在约 130 秒内启动了 9 个 TTS 任务，无法排除账号其他客户端共同消耗 RPM，但本地日志已经证明直接截断触发点是 MiniMax 的 `task_failed`，不是 60 秒输入上限或 PCM 播放队列。旧 TextBridge 的短帧没有丢正文，却放大了发送突发，属于需要修复的本地诱因。
- 随后修复 TextBridge：断点和空白边界必须位于 `min_chars` 之后，正常流式段不再违反最小长度；`config/v0.2.yaml` 将 TTS 断点收敛为句末标点。用该轮 291 字符的 DeepSeek delta 做离线重放，片段数由 26 降至 14，流式段均不少于 8 字；这项结果是确定性分段证据，尚未替代限流窗口恢复后的真实 MiniMax 回放。

### TTS 播放进度调度

本次新增播放进度监控和可选的播放节奏控制。`PcmPlayer` 现在累计当前播放键已经接受、已经被 Windows 音频回调消费和仍在播放器队列中的 PCM；v0.2 控制器另以 MiniMax 已返回的 PCM 总量减去已消费量计算 `audio_remaining_ms`，因此待播放时长包含播放器队列以及已经返回但仍等待进入播放器的音频。控制台记录 `controller.tts_progress`，WebSocket 新增 `tts.progress`，前端在 04 / RESPONSE 中显示已返回、已播放和待播放总时长。

`config/v0.2.yaml` 显式打开 `tts_pacing: true`、`tts_lead_ms: 2000`。第一段完整文本立即发送；后续段进入有界队列。发送器在上一段已有 PCM 返回后，持续检查当前轮全部待播放音频的剩余时长，只有在剩余不超过 2000 ms 时才释放下一段。这样可以继续消费 LLM 增量，又避免首段音频尚未返回时一次性发送所有 `task_continue`。没有播放器或关闭该开关时保留原有立即发送路径。

确定性验证：`tests.test_player` 增加了已入队/已消费 PCM 时长断言；`tests.test_v02.AsyncTests.test_tts_sender_uses_total_remaining_audio_lead_window` 使用两段各 3 秒的模拟音频验证总队列从 3 秒降至 1.9 秒后才发送第二段。当前 Python 测试共 67 项通过，前端 typecheck、test（7 项）和 build 通过。尚未在 MiniMax 限流窗口恢复后进行新的真实云端长文本回放，因此真实服务下的限流改善仍待验证。
